## 收敛后的核心 interface

```ts
interface CombatEngine {
  openCombat(input: NewCombat | RestoreCombat): CombatSession
}

interface CombatSession {
  dispatch(command: CombatCommand): CombatTransition
}

interface CombatTransition {
  revision: number
  snapshot: Readonly<CombatView>
  events: readonly DomainEvent[]
  requiredInput?: RequiredInput
  rejection?: CommandRejection
  checkpoint: CombatCheckpoint
}
```

不暴露 `close()`、`nextTurn()`、`modifyHp()`、EventBus 或 ScriptRegistry，因为它们都会形成绕过原版流程的第二条控制路径喵  

内部仍然使用纯 reducer，但它是 implementation 的 internal seam，不是业务调用方需要理解的 interface 喵  

```ts
reduce(
  bundle: CombatDefinitionBundle,
  state: CombatState,
  command: CombatCommand,
): CombatTransition
```

## 完整运行结构

```mermaid
flowchart LR
    P["玩家 / NPC Agent"] --> C["CombatCommand"]
    C --> S["CombatSession.dispatch"]
    S --> K["纯 CombatKernel"]
    K --> W["Typed ReactionWindows"]
    W --> A["EffectAutomata"]
    A --> I["Intent 验证与聚合"]
    I --> D["DiceTape + 原版公式"]
    D --> T["一次原子提交"]
    T --> E["DomainEvents"]
    E --> U["UI / AI叙事 / 持久化 Adapter"]
```

`dispatch` 会同步自动推进所有不需要外部输入的微步骤，直到出现下一个 `RequiredInput` 喵  

```ts
type RequiredInput =
  | PlayerCommand
  | EffectChoice
  | BoundedAdjudication
  | BeginOutput
```

因此内核中不保存 Promise，也不会像[当前 runner](/E:/Projects/IndependentFront-for-destined-journey/src/sillytavern/combat-runner.ts:331)一样永久挂在 `awaitPlayerInput()` 上喵  

## 原版状态机

```text
RoundOpen
  → 正面状态 tick
  → 战况总览
  → 本轮先攻
  → UnitTurnOpen
      → 攻击槽与动作槽任意顺序消费
      → 必要的选择与反应
      → 士气检查
  → UnitTurnClose
  → 下一单位
  → RoundClose
      → 负面状态与持续伤害 tick
  → 下一轮或 Terminal
  → SettlementCommitted
```

单位会停留在自己的回合，直到攻击槽和动作槽都已消费或显式放弃，解决当前“一个模型响应等于完整单位回合”的偏差喵  

非法 Command、过期 revision 或错误目标都必须保证零状态变化和零骰子消费喵  

`commandId + expectedRevision` 用于串行化并发输入、拒绝 stale command，并对重复提交返回同一个结果喵  

## 脚本与创意能力

非可信技能不再执行任意 JavaScript，而是编译为 `EffectAutomaton` 喵  

每个 automaton 在 typed `ReactionWindow` 中读取同一份 immutable snapshot，并返回一个 intent batch，不再像当前 `emitChain()` 那样依次修改共享参数对象喵  

中央机制代数收敛为以下几类喵  

```ts
type EffectIntent =
  | ModifierIntent
  | OutcomeIntent
  | OverrideIntent
  | PermissionIntent
  | SelectOrRetargetIntent
  | ScheduleIntent
  | SpawnOrDespawnIntent
  | RequestChoiceIntent
```

- `ModifierIntent` 修改命中、伤害、资源消耗等数值槽喵  
- `OutcomeIntent` 请求伤害、治疗、状态或资源变化，但仍须走对应结算窗口喵  
- `OverrideIntent` 在 closed `RuleKey` 上选择内核已经支持的替代规则喵  
- `PermissionIntent` 暂时允许额外行动、越级目标或原本非法的 Command 喵  
- `ScheduleIntent` 表达反伤、延迟爆炸、回合后触发和连锁效果喵  
- `SpawnIntent` 表达召唤，但新单位本轮无行动，下轮才进入先攻喵  

我们明确否决了“任意 TransformRule”设计，因为它本质上会把整个内核重新暴露给 DSL 喵  

法则级能力只能操作内核拥有的 closed `RuleKey`，每个 key 都有独立 schema、scope、权限、神性优先级和 merge policy 喵  

无法表达的新机制会返回 `UnsupportedCapability`，只有当它被至少两个真实技能需要、拥有确定窗口与冲突语义、能够重放且不能由现有 intent 组合表达时，才升级中央 vocabulary 喵  

## 效果事务语义

效果顺序固定为 `window phase → divinity → declared priority → stable source/effect id` 喵  

每个 `EffectProgram` 的 intent batch 是一个原子范围，任何 intent 非法则整批拒绝并产生 `EffectRejected`，但不会取消合法的核心攻击或其他技能效果喵  

核心动作与所有通过验证的效果最终在 Command 末尾一次提交喵  

如果中途需要玩家选择，CombatState 会保存 `ResolutionFrame`、queue cursor、已执行 reaction ID 和 continuation reference，恢复后不会重跑前序效果或再次消费骰子喵  

## 骰池方案

三位 agent 一致认为必须严格保留原版的 output epoch，而不是仅使用普通 seed 喵  

```ts
type BeginOutput = {
  commandId: string
  outputId: string
  dice: readonly D20TupleOf60
  batchHash: string
}
```

每次正文输出开始时显式注入恰好 60 个 d20，并在 state 中记录 `outputId`、batch hash 和 cursor 喵  

骰池耗尽时进入 `RequiredInput.BeginOutput`，adapter 不得暗中补骰，也不能留下半结算动作喵  

Replay artifact 会冻结以下 provenance 喵  

```ts
interface CombatProvenance {
  engineVersion: string
  schemaVersion: string
  rulesetRevision: string
  bundleHash: string
  eventSequence: number
  diceCursor: number
}
```

## 三个压力测试结果

- 濒死锁 1 HP：在 `unit.beforeDown` 返回一次性 replacement 与 charge consumption 喵  
- 反伤：在 `damage.after` 安排新的 Damage outcome，并携带 `rootActionId`、depth 和反射标签，避免无限反射喵  
- 时间停止：通过 `PermissionIntent(grantActionSlot)` 获得受限额外槽位，不能修改 turn scheduler 本身喵  
- 治疗反转：通过 closed RuleKey 把 HP gain 转换为 Damage outcome，转换后的伤害仍重新进入伤害窗口喵  
- 概念免疫：通过带神性优先级的 effect-acceptance rule 拒绝匹配标签，而不是直接删除事件喵  

## 对当前系统的迁移决定

第一刀应放在 `combat-runner → combat execution` 的 seam，而不是继续修补 [EventBus](/E:/Projects/IndependentFront-for-destined-journey/src/sillytavern/game-event.ts:83) 喵  

- `combat-runner` 降为玩家等待、AI 决策和叙事协调器喵  
- `CompatibilityAdapter` 把现有工具参数翻译成 Command 喵  
- DomainEvent projection adapter 继续生成现有 UI `CombatEvent` 喵  
- `combat-damage`、initiative、intention 和 morale 的纯计算可以保留并修正喵  
- StateManager 保留为持久化 adapter，不再充当战斗中的第二状态权威喵  
- [script-executor](/E:/Projects/IndependentFront-for-destined-journey/src/sillytavern/script-executor.ts:164) 的 `new Function` 路径最终由 EffectProgram interpreter 替换喵  

我们否决了在同一场战斗中按 action 或 skill 混用 v2/v3，因为这会重新制造两套行动槽、Buff 生命周期和状态权威喵  

每场战斗创建时必须固定 `engineVersion`、ruleset、definition bundle、DiceTape owner 和 settlement owner 喵  

完整 shadow dual-run 也被否决，因为旧系统含 `Math.random()` 和不确定的 Agent 工具次数，会污染真实骰带且无法公平比较喵  

安全验证只使用纯公式 differential tests、固定 DiceTape replay，以及不写状态的离线 journal replay 喵  

## 建议落地顺序

1. M0：原版协议 contract tests、DiceTape 和 replay harness 喵  
2. M1：基础攻击、战术动作、行动槽、回合、状态 tick 与唯一终局喵  
3. M2：runner CompatibilityAdapter，按整场 feature flag 选择 v2 或 v3 喵  
4. M3：modifier、Buff 和普通状态编译为 EffectProgram 喵  
5. M4：反伤、免死、召唤、延迟效果和法则技能压力测试喵  
6. M5：v3 默认启用，短期保留显式 v2 回滚，然后删除旧战斗接线喵  

最重要的讨论成果是：外部采用简单的 stateful session interface，内部保持纯确定性 reducer，脚本扩展只存在于 transaction 内部 seam，而整场战斗永远只有一个状态、骰子和结算权威喵
