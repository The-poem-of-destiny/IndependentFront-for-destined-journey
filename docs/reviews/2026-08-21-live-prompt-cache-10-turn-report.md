# 生产路径 Prompt Cache 十回合实测报告

> 状态：已完成（2026-08-21 真机实测）
>
> 范围：真实内容包、真实主线大纲、真实角色、10 个玩家回合、制作与交锋场景
>
> 模型：`deepseek-v4-flash`
>
> 计数口径：服务商响应中的 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`、`completion_tokens`

## 1. 结论

“每回合未命中约 30k–60k”作为典型量级成立，但不是每一回合都落在该区间。

- 10 回合总缓存命中：**4,397,824 tokens**
- 10 回合总缓存未命中：**425,052 tokens**
- 10 回合总输出：**82,753 tokens**
- 平均每回合未命中：**42,505 tokens**
- 中位数：**38,718 tokens**
- 最小值：**21,871 tokens**
- 最大值：**84,388 tokens**
- 输入缓存命中率：**91.19%**
- 输入总量（命中 + 未命中）：**4,822,876 tokens**
- 观测到的总 token 流量（输入 + 输出）：**4,905,629 tokens**

缓存本身没有整体失效。高未命中来自每回合 7 个常驻 Agent 各自携带动态上下文，再叠加制作、角色生成、物品生成等侧链。缓存命中量很大，但各请求中第一个变化 token 之后的动态后缀仍按未命中计费。

## 2. 测试方法

1. 使用生产应用与本地真实内容包，不使用 mock 或 token 估算。
2. 使用已保存的 DeepSeek API 配置，直接读取服务商返回的缓存 usage 字段。
3. 创建新角色“卡修·铁星”：人类、锻造师学徒、T1 Lv.1。
4. 初始装备包含精铁长剑、链甲套装、精工细作、荣耀打击、精铁锭材料包与生命药剂。
5. 生成 3 章主线大纲，剧情偏向战斗与探索。
6. 完成 10 个玩家输入回合，覆盖正式制作、接任务、探索、交锋、撤退、汇报与主线调查。
7. 每回合等待全部侧链结束后，从调试面板逐 Agent 记录 provider usage。
8. 调试面板默认汇总排除 `memory_recall`；本报告将其重新加入每回合总数。

创角开局首轮另产生 8 个 Agent 调用：命中 **423,680**、未命中 **46,519**。剧情大纲生成发生在创角页，该页面没有显示 provider 缓存明细，因此不将其伪装成可测数据，也不计入下面 10 回合。

## 5. Token 使用分析

### 5.1 缓存是有效的，但命中量不能抵消多个动态后缀

叙事 Agent 每回合稳定命中 165,376 tokens，十回合输入命中率 95.61%；角色生成和物品生成的输入命中率分别达到 98.75% 和 96.93%。这说明大型静态世界书和固定系统提示词被缓存良好，不应把问题归因于“静态前缀顺序完全破坏缓存”。

真正的问题是每个回合至少产生 7 次不同 Agent 请求。各 Agent 在已缓存前缀之后都追加本轮玩家输入、正文、角色状态、剧情事件、记忆、任务、物品或上游输出。即使单个请求只剩 2k–10k 未命中，跨 Agent 相加仍然稳定达到 30k 以上。

### 5.2 最贵的是重复消费正文与历史的后置 Agent

前三大未命中来源为：

1. 叙事生成：75,854。
2. 剧情复检：74,538。
3. 记忆摘要：67,324。

三者合计 **217,716**，占全部未命中的 **51.2%**。剧情复检会重新读取最近 4 轮历史、本轮用户输入、本轮完整正文和本轮记忆摘要；记忆摘要会读取剧情事件、本轮完整正文、角色状态、最近 4 轮历史与已有记忆。它们在正文生成之后再次消费大段高频变化内容，因此缓存命中率只有约 44%–48%。

### 5.3 `historySlice` 当前没有在生产 prompt 路径生效

配置与设置界面仍保存 `historySlice`，并宣称按每条历史正文保留 800/1500 字；但生产 `NARRATIVE` resolver 只按 `layers * 2` 选择消息，然后把每条消息完整拼入 prompt，没有执行字符截断。

这使长叙事在以下 Agent 中被重复完整注入：

- Story：`historyLayers=6`。
- Memory summary：最近 4 轮。
- Plot post check：最近 4 轮。
- Plot pre check / memory recall：最近 3 轮。
- Request dispatcher / vars update / sidechain：最近 1 轮或本轮完整正文。

这是本次实测中最明确、最可直接修复的生产回归。

### 5.4 冷启动与预热差异明显

- 回合 1–5 平均未命中：**54,365**。
- 回合 6–10 平均未命中：**30,645**。
- 仅看七个常驻 Agent，前五回合平均 **44,473**，后五回合平均 **28,298**。

下降说明 DeepSeek 前缀缓存会随相同 Agent 的稳定前缀逐步预热。回合 1 的制作侧链和回合 2 的首次角色生成造成峰值；回合 10 再次生成新角色和物品，使未命中回升到 39,950。

### 5.5 Agentic 工具调用会放大“总 token 流量”

角色生成等 Agent 可以进行多轮工具调用。`chatWithTools()` 每轮把之前的 assistant/tool 消息追加到 conversation，再重新发送整个会话，并把各内轮 usage 累加到本次 Agent 记录。

因此角色生成在回合 10 命中了 979,712 tokens。其未命中仅 7,105，缓存效率很高，但仍产生极大的 provider token 流量和延迟。优化时需要同时观察：

- 未命中 token（直接的新输入成本）。
- 命中 token（通常仍有较低缓存读取成本）。
- 输出 token。
- 工具调用轮数与累计延迟。

只盯未命中会漏掉 agentic 侧链的总体吞吐风险；只盯总 token 又会误判缓存完全无效。

## 6. 制作、战斗与剧情覆盖结果

### 6.1 制作

制作链路成功。`craft_gen` 与 `item_gen` 均真实调用，材料包被消费，精铁匕首成功进入角色背包。

### 6.2 战斗

战斗链路未真正启动。回合 4–7 已发生明确交锋，角色损失 15 HP 并获得“虎口擦伤”，但 `combat_v3` 调用数为 0，也未出现战斗就绪面板。

回合 5 明确要求启动正式战斗系统；回合 6 进一步在玩家输入中提供完整 `combat_trigger`。当轮 request dispatcher 仍只返回 `<json>` 与 `<char_update_request>`，没有生成系统提示词强制要求的 `<combat_trigger>`。

因此本次覆盖的是“真实叙事交锋 + 状态结算”，不是“独立战斗 Agent/战斗面板”。这是一个独立于缓存问题的生产链路缺陷。

### 6.3 剧情

主线大纲成功生成，标题为“炉火初燃：铁星之誓”，包含 3 章。矿道异常、冰冷铁锈气息和公会调查明显受到大纲影响，`plot_pre_check` 与 `plot_post_check` 每回合都真实调用。

但十回合结束后 UI 仍显示章节进度 `0/3`。最后一轮剧情复检返回空 `eventUpdates`。这可能是触发条件尚未满足，也可能是事件标题/证据过于保守，需要针对生成的大纲事件条件另做一次可见性诊断，不能在本报告中直接判定为事件状态机错误。

## 7. 修正优先级

### P0：恢复 `historySlice` 的生产执行

在 `NARRATIVE` resolver 中按 Agent 配置或显式参数对每条历史消息进行截断，并添加包含长正文的回归测试。该修复能同时降低 story、memory recall、plot pre/post、memory summary、vars update 和侧链 prompt。

### P1：为每个占位符记录字符/token 贡献

在最终 prompt 组装时记录各区块长度，例如 `LORE_BOOK_STATIC`、`NARRATIVE`、`CHARACTER_STATE`、`PLOT_EVENTS`、`AGENT.STORY`。没有该数据时只能从 provider 的整请求计数反推，无法精确验证一次优化究竟减少了哪个动态区块。

### P1：缩减后置 Agent 的动态投影

- 剧情复检不应同时拿 4 轮完整历史、本轮完整正文和完整记忆摘要；优先保留正文与结构化摘要。
- 记忆摘要不应重复携带大段角色完整状态与 4 轮正文；只投影本轮涉及角色与活跃事件。
- 状态更新只需要调度器明确引用的角色、物品和任务，而非完整集合。

### P1：增加按场景的 turn budget

分别建立以下实测预算并在调试面板报警：

- 普通剧情回合。
- 主线开启回合。
- 制作回合。
- 新角色/物品侧链回合。
- 战斗回合。

建议第一阶段以“预热后的普通主线回合全部 Agent 未命中 ≤25k”为目标；本次回合 8–9 已接近该量级，说明该目标不是脱离现状的猜测。

### P2：限制 agentic 工具轮次与返回体积

对 char/item/craft Agent 记录每个内部工具轮次的 hit/miss/output，限制重复查询，并缩短工具结果投影。否则即使 miss 很低，也会继续产生接近百万级的缓存读取流量。

### P2：单独修复战斗触发可靠性

为 request dispatcher 增加“正文已真实动武但未输出 combat_trigger”的确定性兜底或结构化验证，避免模型违反强制规则后静默吞掉独立战斗系统。
