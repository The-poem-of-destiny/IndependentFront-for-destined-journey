## 执行摘要

在本次验证的 1 个默认主题下，当前 UI 已形成清晰而独特的暗色叙事 RPG 视觉身份。首页主行动明确，游戏主界面的桌面三栏构图完整，角色确认页的信息密度控制良好，装备页的分类、品质和搜索组合也证明项目已有可复用的复杂目录交互模式。全局焦点环与减少动画支持已经存在，说明设计系统并非从零开始补可访问性。除源码层可直接确认的共享结构问题外，本文的视觉、对比度、素材和主题表现结论不得外推为对全部 10 个主题的验证结果。

当前最重要的问题集中在三个边界：

1. **创建状态完整性：** 被视觉禁用的装备仍可通过卡片内按钮选中，store 与最终提交均没有再次校验，能够绕过点数或身份限制。
2. **响应式状态模型：** 游戏页把桌面画布硬限制为至少 900px，再由多层 `overflow: hidden` 裁掉超出部分；768px 下右侧状态栏不可见且无法横向访问。
3. **原生交互语义：** 难度、背景、命定核心、步骤导航和共享弹窗中存在一批“看起来可操作、但键盘或辅助技术无法正确操作”的伪控件。

本次共登记：

- **1 项 P0：** 可生成违反创建约束的存档状态；
- **5 项 P1：** 主流程在窄屏或键盘操作下不可完成、不可访问或不可恢复焦点；
- **6 项 P2：** 目录发现、触控目标、空态、状态表达和测试覆盖不足；
- **1 项 P3：** 首页次要信息的可读性与产品文案问题。

## 优先级定义

- **P0：** 常规可达路径会破坏承重状态约束，应阻断发布。
- **P1：** 主流程在常见设备或输入方式下不可用，或存在显著可访问性失败。
- **P2：** 不阻断主流程，但会明显降低理解、发现、操作效率或回归安全性。
- **P3：** 视觉与文案抛光问题，影响有限。

## 已确认的优势

### 1. 产品视觉身份稳定

首页、创建页与游戏页共享一致的暗色、樱粉、低饱和材质与装饰线语言。游戏页明显是“被装饰的游戏应用”，而非通用后台或网页卡片集合。桌面游戏页的左侧场景、中央叙事、右侧角色状态三栏关系清楚，角色状态的 HP / MP / SP / EXP 也采用了稳定的语义色。

### 2. 复杂目录已有成熟范例

装备页同时提供类型、来源、品质和搜索，右侧保留已选项目与消费汇总。该结构可以直接复用于命定核心和角色启用，而不需要发明第二套目录交互（`src/ui/components/create/CreateStepSelections.vue:65-80,110-132`）。

### 3. 确认页完成了必要的风险收口

确认页把角色身份、起始地点、资源、属性、装备、技能、道具、背景和剧情大纲集中呈现，并明确说明剩余转生点数的去向。与前面高密度步骤相比，它提供了有效的提交前停顿。

### 4. 基础可访问性设施已经存在

全局 `:focus-visible` 样式已经定义（`src/ui/styles/base.css:66-71`），系统级和应用内的减少动画路径也会统一压缩动画与过渡时长（`src/ui/themes/variables.css:134-170`）。问题主要是部分自定义点击面没有进入这套基础设施，而非全局完全缺失。

## 审查发现

### UI-01 — 视觉禁用的装备仍可被选中

- **优先级：** P0
- **影响页面：** 角色创建 / 装备选择
- **归属边界：** 创建约束与最终存档完整性

装备列表把 `!store.canSelect(item)` 传给卡片的 `disabled` 外观（`src/ui/components/create/CreateStepSelections.vue:124-131`），但卡片内部“选择”按钮没有禁用，仍会无条件发出 `select`（`src/ui/components/create/SelectableCard.vue:65`）。store 的添加逻辑没有再次调用 `canSelect`（`src/ui/stores/create-store.ts:734-761`），该步骤本身始终视为可通过（`src/ui/stores/create-store.ts:150-152`），最终 `startJourney()` 也没有点数或资格总校验（`src/ui/stores/create-store.ts:1807-1817`）。

**触发条件：** 玩家对点数不足、种族不符或身份不符的灰色项目点击卡片内部“选择”。

**实际影响：** 玩家可以绕过创建限制并完成提交，产生负点数或不符合资格约束的存档。

**整改建议：**

1. 禁用卡片内部按钮并阻止卡片发出选择事件；
2. store mutation 必须独立校验 `canSelect`，不能信任 UI；
3. `startJourney()` 在任何持久化之前做一次完整创建约束校验；
4. 增加“直接调用 mutation”和“点击禁用卡片按钮”两层回归测试。

### UI-02 — 游戏页缺少窄屏布局状态，右侧 HUD 被直接裁切

- **优先级：** P1
- **影响页面：** 游戏主界面
- **归属边界：** 游戏壳响应式布局

`GamePage` 使用 `width: 100vw`、`min-width: 900px` 与 `overflow: hidden`（`src/ui/components/game/GamePage.vue:474-483`），内部 `.game-body` 继续裁切（`src/ui/components/game/GamePage.vue:487-492`），`body` 与 `#app` 同样禁止溢出（`src/ui/styles/base.css:16-29`）。768px 下页面仍按至少 900px 排版，但没有任何横向滚动容器；作为末端 flex 子项的 HUD 因此从右侧消失。

1024px 虽未完全裁切，但已经进入几何冲突区。场景栏使用 `calc(25% - rail)` 且 `min-width: 200px`（`src/ui/components/game/ScenePanel.vue:452-458`），HUD 使用 `25%` 且 `min-width: 240px`（`src/ui/components/game/StatusHUD.vue:12-18`）。考虑 `--rail-w: 4.2rem` 后，25/50/25 的约定约在 1069px 以下开始破裂。现有 1100px 媒体查询只调整内部素材，没有改变外壳状态。

**实际影响：**

- 768px 下 HUD 内容不可见且不可平移；
- 键盘焦点仍可能进入屏幕外的 HUD 控件；
- 1024px 下中央叙事区提前被侧栏最小宽度挤压；
- 浏览器缩放会进一步放大问题。

**整改建议：** 给游戏壳定义明确的响应式状态，而非继续缩小桌面三栏：

- 约 1100px：进入紧凑桌面态，先收敛装饰与次要信息；
- 约 900px：中央叙事保持主面，Scene 与 Status 改为可访问的抽屉、标签页或覆盖层；
- 抽屉需管理初始焦点、关闭后焦点恢复，并确保隐藏内容不可 tab；
- 从结构面移除 `zoom: 1.1`，用字号、间距和素材 token 控制密度。

### UI-03 — 难度与背景卡片阻断键盘完成创建

- **优先级：** P1
- **影响页面：** 角色创建 / 难度选择、背景故事
- **归属边界：** 必选项的原生交互语义

难度卡片只在 `AppCard` 上监听 `@click`（`src/ui/components/create/CreateStepDifficulty.vue:18-31`），而 `AppCard` 输出普通 `<div>`（`src/ui/components/shared/AppCard.vue:12-23`）。背景预设同样使用带点击处理的 `<div>`，没有 `role`、`tabindex`、键盘事件、`aria-checked` 或 `aria-disabled`（`src/ui/components/create/BackgroundList.vue:107-116`）。

真机 DOM 检查确认六张难度卡片均不在可聚焦集合内，而未选择难度时“下一步”保持禁用。

**实际影响：** 键盘、开关设备与部分屏幕阅读器用户无法完成创建的第一个必选步骤；辅助技术也无法得知当前选中状态。

**整改建议：** 使用原生 radio + label 组成 `fieldset`，或实现完整的 radiogroup，包括选中状态、方向键切换与禁用语义。

### UI-04 — 命定核心的 radio 焦点与键盘处理不在同一元素

- **优先级：** P1
- **影响页面：** 角色创建 / 命定核心
- **归属边界：** 自定义 radio 组件

`role="radio"` 与 `tabindex="0"` 放在 `.core-row`（`src/ui/components/create/CreateStepDestinyCore.vue:65-74`），Enter / Space 处理却放在不可聚焦的子元素（`src/ui/components/create/CreateStepDestinyCore.vue:76-81`）；工坊核心列表重复了同一结构（`src/ui/components/create/CreateStepDestinyCore.vue:120-134`）。列表外层没有 `radiogroup`，也没有方向键逻辑。

**实际影响：** Tab 能到达看似正确的 radio，但 Enter / Space 不能选择；读屏器获得的集合和选择关系也不完整。

**整改建议：** 把焦点、角色、状态和键盘处理放在同一元素；优先改为原生 radio。若保留自定义实现，必须补齐 radiogroup 与箭头键行为。

### UI-05 — 设置页在手机宽度保留固定侧栏，内容区失去可读性

- **优先级：** P1
- **影响页面：** 系统设置
- **归属边界：** 设置页响应式导航

设置页始终保留 180px 左侧导航（`src/ui/components/settings/SettingsPage.vue:313-323`），内容区继续使用 32–40px padding（`src/ui/components/settings/SettingsPage.vue:447-454`），没有窄屏覆盖。390px 实测时，导航占据 180px，内容在 padding 前只剩 210px，API 标题与说明已经压缩到每行一至两个汉字。

**实际影响：** 手机宽度下设置内容虽仍存在于 DOM 中，但视觉上和阅读上基本不可用。

**整改建议：** 在手机态把侧栏改为顶部下拉、分组抽屉或独立导航页；内容页占满宽度，并保留清晰的当前分区标题与返回路径。

### UI-06 — 共享弹窗没有 dialog 与焦点管理契约

- **优先级：** P1
- **影响页面：** 所有 `AppModal` 调用方
- **归属边界：** 共享弹窗基础组件

`AppModal` 目前只锁定 body 滚动并监听 Escape（`src/ui/components/shared/AppModal.vue:43-69`）。遮罩与内容没有 `role="dialog"`、`aria-modal`、标题关联、初始焦点、焦点陷阱或关闭后焦点恢复（`src/ui/components/shared/AppModal.vue:76-106`）。真机打开角色预设弹窗后，焦点仍停留在遮罩背后的触发按钮。

**实际影响：** 键盘焦点可以游离到背景页面；屏幕阅读器无法可靠识别弹窗边界；关闭后用户可能失去操作位置。

**整改建议：** 把 dialog 语义、标题描述关联、初始焦点、Tab 循环、Escape 与触发器焦点恢复统一收进 `AppModal`，调用方只提供标题、内容和首选初始焦点。

### UI-07 — 八步进度条使用按钮语义，却没有导航行为

- **优先级：** P2
- **影响页面：** 全部角色创建步骤

步骤节点渲染为 `<button>`，完成步骤会获得 `tabindex="0"`（`src/ui/components/create/CreateSteps.vue:32-46`），样式又给 active / done 状态设置 pointer cursor（`src/ui/components/create/CreateSteps.vue:83-90`），但组件没有 click / keyboard handler 或导航事件。页面只接了底部上一步、下一步（`src/ui/components/create/CreatePage.vue:84-90`）。

**实际影响：** 鼠标和键盘用户都被明确暗示“可以返回已完成步骤”，但激活按钮没有任何效果；无效按钮还进入了 Tab 顺序。

**整改建议：** 二选一：实现经过校验的随机步骤导航；或改成非交互 progress / list 语义，并移除按钮、pointer cursor 与 tabindex。

### UI-08 — 最大的两个创建目录缺少发现工具，并暴露作者态文本

- **优先级：** P2
- **影响页面：** 命定核心、角色启用

命定核心直接渲染全部条目，只提供展开与摘要（`src/ui/components/create/CreateStepDestinyCore.vue:64-151`）。角色页同样直接渲染全部条目（`src/ui/components/create/CreateStepCharacters.vue:24-42`），没有搜索、过滤、分组或全选 / 全不选。真机数据为 29 个角色，部分摘要直接显示 EJS 条件、变量名和作者指令文本。

**实际影响：** 用户只能串行扫描大量截断卡片，已知目标难以定位；作者态实现文本破坏世界观沉浸感，也让卡片摘要失去辨识价值。

**整改建议：** 复用装备页的搜索和过滤结构；角色页增加全选 / 全不选与可选分组；为玩家卡片建立独立的展示摘要字段或净化层，不直接截断原始世界书正文。

### UI-09 — 多个共享与紧凑控件低于项目 36px 目标

- **优先级：** P2
- **影响页面：** 创建页、首页提示、设置页、共享弹窗、游戏侧栏

设计规范要求交互目标至少 36px 高（`docs/design.md:433-434`），但 `AppButton` 的尺寸只有 padding，没有最小高度（`src/ui/components/shared/AppButton.vue:48-65`）。真机测量中，`sm` 约 26.7px，`md` 约 33.9px；弹窗关闭按钮明确为 28×28（`src/ui/components/shared/AppModal.vue:184-197`）。装备搜索清除按钮为 16×16（`src/ui/components/create/CreateStepSelections.vue:274-287`），命定核心取消按钮为 24×24（`src/ui/components/create/CreateStepDestinyCore.vue:293-304`）。折叠游戏侧栏的可用宽高也低于 36px。

**实际影响：** 触控、运动障碍和高缩放用户更容易误触；越是窄屏，最需要紧凑导航时目标反而越小。

**整改建议：** 在共享按钮与图标按钮层统一 `min-width` / `min-height: 36px`；纯图标关闭、删除与清除操作应扩大点击面而不是只扩大图标。

### UI-10 — 游戏空态缺少可执行的首次行动引导

- **优先级：** P2
- **影响页面：** 游戏主界面 / 尚无叙事消息

中央叙事区只有“等待冒险开始”和“在下方输入你的行动来推进故事”，大部分画布为空。输入框给出发送快捷键，但没有示例行动、建议开场或解释当前可用能力。

**实际影响：** 新玩家进入最重要的游戏页面后，知道“要输入”，却不知道“可以输入什么”或系统会如何响应。

**整改建议：** 在首回合空态提供 2–4 个可直接使用或填入输入框的行动示例；示例应根据地点、在场角色和开局背景生成，而不是长期固定文案。

### UI-11 — 剧情规划的模式与主行动表达矛盾

- **优先级：** P2
- **影响页面：** 角色创建 / 剧情规划

模式选择为“关闭”时，页面仍突出“生成剧情大纲”按钮，并提示该操作会调用 AI。页面其余区域几乎为空，导致按钮成为视觉主行动，但当前模式又表示功能关闭。

**实际影响：** 用户无法判断按钮会自动切换模式、生成后仍保持关闭，还是当前根本不可用。

**整改建议：** 模式关闭时隐藏或禁用生成区，并解释如何开启；选择主线或支线模式后再显示对应配置与生成 CTA。

### UI-12 — 缺少承重响应式与键盘回归测试

- **优先级：** P2
- **影响范围：** 游戏壳、创建流程、共享组件

`GamePage.test.ts` 只检查外壳存在，部分断言使用 `exists() || true`，没有视口、DOMRect 或键盘遍历断言（`src/ui/components/game/GamePage.test.ts:83-94`）。当前 768px 裁切、伪控件和弹窗焦点问题因此不会触发测试闸门。

**整改建议：** 至少覆盖：

- 1440×900、1024×768、768×768 三档游戏壳；
- 所有可见区域位于视口内，中央叙事和输入区保持可用宽度；
- 隐藏抽屉内容不可聚焦，打开 / 关闭后焦点归属正确；
- 仅用键盘完成难度、核心、背景与提交前导航；
- 禁用装备不能通过 DOM 点击或直接 store mutation 加入。

### UI-13 — 首页内容提示偏开发者语言，页脚对比度过低

- **优先级：** P3
- **影响页面：** 首页、设置页公共内容提示

“检测到本地真实内容，导入内容包以恢复完整默认与后续更新”需要用户理解“真实内容”“内容包”和“默认更新”等内部概念，且横幅在首页最上方长期占据高视觉权重。页脚则同时使用 `0.75rem`、muted 文本和父级 `opacity: 0.4`（`src/ui/components/home/HomePage.vue:873-885`）；真机计算后的对比度约为 1.85:1，远低于小字号文本通常需要的 4.5:1。

**整改建议：** 用玩家结果描述内容状态与行动后果；页脚移除父级 opacity，改用达到目标对比度的明确颜色 token。

## 建议整改顺序

### 第一批：阻断级与主流程可达性

1. 修复装备选择的 UI + store + 最终提交三层校验；
2. 为游戏壳实现 1100px / 900px 两级响应式状态；
3. 把难度、背景、命定核心改成可键盘完成的原生选择控件；
4. 为以上路径补承重回归测试。

### 第二批：共享交互边界

1. 收口 `AppModal` 的 dialog 与焦点契约；
2. 给设置页增加手机导航形态；
3. 裁定步骤条是导航还是进度展示，并统一语义；
4. 在共享按钮层落实 36px 最小目标。

### 第三批：理解与发现效率

1. 给命定核心和角色目录增加搜索、过滤与批量操作；
2. 建立玩家态摘要，隔离世界书 / EJS 作者态正文；
3. 调整游戏首回合空态与剧情规划状态文案；
4. 收敛首页内容提示和低对比度次要文本。

## 建议验收标准

- 不满足 `canSelect` 的项目在 UI、store 和最终提交三层均无法进入存档；
- 768px 宽度下，游戏的叙事、输入、Scene 与 Status 均有明确且可键盘访问的入口，不存在不可平移的裁切；
- 390px 宽度下，设置内容正文不因固定导航而压缩成逐字换行；
- 仅用 Tab、Shift+Tab、方向键、Enter、Space 和 Escape 可以完成创建主路径并正确操作弹窗；
- 所有隐藏抽屉和弹窗背景内容不会进入 Tab 顺序；
- 共享按钮与图标按钮满足项目至少 36px 的点击目标；
- 玩家态卡片不显示 EJS、变量名、正则或作者指令；
- 上述行为在至少 1440、1024、768 与 390 四档自动化回归中有覆盖。

## 审查局限

- 项目共有 10 个主题，本次只走查了审查时启用的 1 个默认主题，其余 9 个主题均未验证。本文关于视觉层级、色彩、对比度、素材、装饰和主题内响应式表现的结论只适用于该默认主题；不得据此判定全部主题通过。结构层 `zoom` 的主题差异仍需在后续十主题矩阵中逐一复测。
- 视觉走查和 DOM 检查不能替代 NVDA、VoiceOver 等真实屏幕阅读器测试，因此本报告不声明完整 WCAG 合规。
- 未调用真实模型，剧情生成等待态、失败态、流式输出与长正文滚动未纳入本次审查。
- 视觉截图保留在本地审查产物中；为遵守仓库“仅 `.md` 可直推 `master`”的规则，本报告提交不包含二进制截图。

## 总体判断

UI 的视觉方向不需要推倒重来。最有价值的工作不是继续增加装饰，而是把现有设计系统补成一套可靠的交互与响应式状态模型：约束在 store 收口、窄屏切换布局、选择使用原生语义、弹窗统一管理焦点。完成第一、二批后，当前桌面端已经具备的高完成度才能稳定延伸到窄屏、键盘和辅助技术用户。
