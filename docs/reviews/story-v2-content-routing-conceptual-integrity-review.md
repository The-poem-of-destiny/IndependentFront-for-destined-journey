# Story v2 与内容路由：Conceptual Integrity 代码审查

## 1. 审查结论与范围

**结论：共享机制已经建立，但部分生产入口尚未迁移完成，部分调用方仍在自行实现共享规则，本次更新尚未完成结构收敛。**

本报告汇总两轮针对未提交区代码的审查，共 8 项发现：

- 4 项已通过直接调用复现的行为缺陷。
- 4 项经代码追踪确认的结构性维护问题；不将未来可能发生的漂移描述成已经发生的故障。

审查方法为 **“同一种事情，只保留一条实现路径”**：在源头统一语义，完成调用方迁移，删除被替代的实现，不通过下游补丁、额外配置或兼容旁路掩盖分歧。

### 范围与限制

- 对象：审查时未提交的 Story v2、内容路由、记忆归档、预设、工坊与相关 UI / 测试变更，并沿调用链检查必要的现有代码。
- 依据：源码、相关测试和直接调用结果；没有阅读项目设计文档来推定实现要求。
- 未使用 subagent，未修改业务代码，未发送真实 LLM 请求。
- 本报告记录审查时的工作区状态，不绑定某个已提交版本。行号为定位线索，后续修改时应同时按符号名定位。
- 本报告不是全仓库质量认证，也不代表已经通过完整本地 gates。

## 3. 已复现的行为缺陷

### CI-01：工坊路由协议只迁移了消费端

`src/ui/stores/workshop-store.ts:364: half-move 工坊旧授权路径已删除，但安装产物仍不包含新路由声明。 → 在工坊解析与安装边界完成条目协议迁移。`

**代码证据**

- `workshop-store.ts` 删除了安装后向 Agent 世界书清单授权的步骤。
- `src/core/workshop/workshop-install-plan.ts:156–176` 的 `planInstall` 构造条目时只生成 `extra.workshop`，没有保留或生成 `extra.lore`。
- 新路由以条目的 `extra.lore.audiences` 为读取范围来源；未声明时没有 Agent 可以读取。

**复现与影响**

直接调用安装计划生成器，再把产物交给 `getEntriesForAgent('story', books)`：安装产物有 1 条启用条目，Story 可读条目数为 0。在安装计划入参中附带路由元数据，也不会被该构造过程保留。

因此，工坊安装可以报告成功，但内容不能进入 Agent 上下文；更新同样重新构造条目，会抹掉之前手工补充的路由声明。

**收敛建议**

- 在工坊数据进入引擎的边界，明确并保留逐条目路由声明。
- 处理已安装工坊条目的迁移，而不是只修复新安装。
- 运行时继续共用现有条目路由机制，不恢复逐 Agent 挂书清单。
- 旧工坊条目的迁移授权必须有可说明的依据；若历史有效范围已无法恢复，应明确提出行为决策，不能猜测为“全部 Agent 可读”。

**验收标准**

安装和更新得到的条目可按声明被读取；更新不无声丢弃路由元数据；旧安装数据有明确的迁移或拒绝处理结果。

### CI-02：已选预设在 v2 中被当成空预设

`src/core/prompts/story-context-v2.ts:202–220: split-path 新旧组装器分别解释预设格式，v2 丢弃 fixedSystem/fixedExamples。 → 共享预设归一化读取，只保留消息布局差异。`

**代码证据**

- `buildStoryContextV2Messages` 只读取 `settings.prompts`。
- 没有普通条目时，直接使用 `config.systemPrompt` 或引擎模板存根。
- 旧组装器通过 `assemblePresetContent` 支持 `fixedSystem/fixedExamples` 格式。
- `AgentPreset` 仍声明这两个字段，生产加载路径也没有统一将其转换为 `settings.prompts`。

**复现与影响**

对同一个已选预设分别调用两个组装器：

| 检查项                           | 旧组装器 | v2 组装器                        |
| -------------------------------- | -------- | -------------------------------- |
| 是否包含已选预设的 `fixedSystem` | 是       | 否                               |
| v2 首段实际内容                  | 不适用   | `config.systemPrompt` 的替代内容 |

用户选择的系统指令和示例因此可以在 v2 中无声消失，而不是收到不支持该格式的错误。

**收敛建议**

在共享预设读取入口统一处理格式和有效内容；新旧模式分别处理布局，不分别判定“预设是否为空”。不要仅在 v2 追加一条新的局部 fallback，继续保留两套格式解释规则。

**验收标准**

同一份受支持预设，无论进入哪种布局，都保留其有效指令和示例；五区占位条目的存在不会改变这一结论。

### CI-03：整书授权破坏逐条目隔离

`src/ui/components/settings/WorldBookEditor.vue:324–331: split-path 批量编辑把授权并集作为每条记录的新真值。 → 批量操作只改变本次点击的 Agent 授权。`

**代码证据**

- `bookAudiences` 是所有条目读取范围的并集。
- `toggleAudience` 对并集增删一个 Agent 后，将整个结果写入每个条目。
- 同一编辑器的条目弹窗又允许各条目维护不同读取范围。

**复现与影响**

原始授权：

```text
A → story
B → char_gen
```

勾选整书的 `lore_select` 后，实际结果为：

```text
A → story, char_gen, lore_select
B → story, char_gen, lore_select
```

用户只操作了一个 Agent，却同时把 A 授予 `char_gen`、把 B 授予 `story`。原有隔离被无声取消。

**收敛建议**

逐条目授权继续作为唯一真源。批量操作只对每条记录增删本次操作的 Agent，保留其他授权；聚合展示值不能反向覆盖条目状态。

**验收标准**

对授权不同的条目执行一次批量增删，只改变目标 Agent 的权限，不改变其他 Agent 的读取范围。

### CI-04：总结 Agent 的请求参数随入口变化

`src/ui/lib/game-pipeline.ts:2816、2934: split-path 主总结、历史补建和归档重写分别投影同一 Agent 配置，后两者漏传部分采样参数。 → 统一 AgentConfig 到请求参数的投影。`

**代码证据**

- 主流程在 `src/core/agents/agent-orchestrator.ts` 中构造请求，传入 `temperature/maxTokens/topP/frequencyPenalty/presencePenalty`。
- `backfillMissingStorySummaries` 与 `rewriteArchiveDetailsFromSource` 各自手写请求，只传 `model/temperature/maxTokens`。
- `AgentClient` 对缺席参数采用源级默认或提供方默认，不能恢复调用方未传入的 Agent 覆写值。

**复现与影响**

直接调用归档重写入口，配置包含：

```json
{
  "topP": 0.2,
  "frequencyPenalty": 0.8,
  "presencePenalty": 0.6
}
```

捕获到的请求参数只有 `model/temperature/maxTokens`，上述三个参数均未进入请求。该验证没有发送真实网络请求。

**收敛建议**

统一已解析 Agent 配置到请求参数的投影。主流程、补建和归档重写只提供各自的消息内容，不各自挑选配置字段。不要仅在两处分别补上遗漏字段后结束修复。

**验收标准**

同一 Agent 的有效采样配置在各调用入口一致生效；不同消息契约不改变配置优先级。

## 4. 结构性维护问题

### CI-05：预设预处理提取后没有完成迁移

`src/core/prompts/preset-loader.ts:167、240: half-move 新共享函数与旧的跨条目预处理实现并存。 → 迁移旧组装器并删除被替代的实现。`

`preprocessPresetEntryContents` 已经实现了宏检测、跨条目收集 setvar、逐条替换；`assemblePresetContent` 却仍保留另一套相同流程。v2 与旧模式各走一套，下次修改宏语义仍需同步维护。

**建议**：旧组装器也消费共享的条目预处理结果，只保留拼接、空白处理和默认上下文追加的布局职责。需要保持已有可观察输出语义，不应借收敛随意改变提示词字节。

预览保留随机宏、运行时展开随机宏，是实际语义差异，不要求把预览强行并入相同执行流程。

### CI-06：摘要记录构造规则在 UI 管线复制

`src/ui/lib/game-pipeline.ts:2666、2830: split-path 正常总结和历史补建分别构造同一种 StoryTurnSummaryRecord。 → 在记忆模块保留一个记录构造实现。`

两处都维护来源、游戏时间、人物、地点、主题、顺序、内容、事件名、ID 和创建时间的写入规则。生成时机不同，但落库记录的语义没有不同。

**建议**：在记忆模块提供一个纯记录构造函数，由调用方传入原回合、解析片段、存档标识及 ID / 时间来源；两条流程继续分别决定何时生成、是否归档和何时提交。删除两份手写字段映射，不引入服务工厂或可配置构造策略。

**验收重点**：以后新增一个摘要字段或修改来源绑定，只需改变一个构造入口；正常总结与补建仍绑定各自的原回合事实。

### CI-07：重试记录持有覆盖信息的第二份真值

`src/core/types/types.ts:1704–1709: second-truth retry 同时持久化 archives 及其覆盖聚合副本。 → 覆盖并集从保存的 archive 原始快照派生。`

重试记录已经包含 `archives`，却还单独保存：

- `coveredSegmentIds`
- `coveredSources`
- `coveredSegmentFingerprints`

`game-pipeline.ts:2713–2724` 手工生成这些聚合值。备份导入分别重映射父记录和内部归档，校验、清理又消费父记录副本，因此维护者必须同时理解并维护两层覆盖信息。

**建议**：保留每条 archive 的原始来源及覆盖快照，重试级并集按需派生；重试记录只持久化独立的重试事实。不要通过额外同步任务维护聚合副本。

这里不建议删除归档自身的来源指纹，也不允许用当前正文重新计算来替代历史快照。原始快照保护的是来源有效性，父级聚合副本只是重复表达。

由于涉及持久化与备份形状，实施时必须处理已有记录的读取和导入边界，并保留最小可运行的格式 / 重放契约测试。

### CI-08：预算判据没有成为真正的共享入口

`src/core/agents/agent-orchestrator.ts:730–734: split-path 诊断调用预算函数，实际阻断请求却重新实现判断。 → 裁剪、估算、阻断和诊断共用预算规则。`

- `story-context-mode.ts` 已有 `assessStoryContextBudget` 和字符换算常量。
- UI 诊断消费该函数。
- 编排器手写 `Math.ceil(totalChars / 1.5) + outputReserve` 的超限判断。
- 组装器在移除项和分类估算中也分别写入相同换算规则。

目前没有将这些重复实现描述为已经造成预算误判；问题是同一预算语义仍有多个修改入口。

**建议**：在现有预算模块内统一字符换算、窗口有效性、输入额度和超限判据。最终是否允许请求由这一判据决定，诊断展示同一个结果。保持粗估 token 与 provider 实际 usage 的区别，不增加第二个预算开关。

## 5. 应保留的设计与边界

本次审查不把所有分支和保护措施都视为重复。以下设计方向是合理的：

1. **来源校验集中化**：`story-memory-source.ts` 集中消息指纹、摘要语义指纹和归档覆盖校验，读取、提交及回退复用规则。
2. **向量召回共享化**：旧记忆与 v2 共用 `recallByEmbedding`，调用方只提供真实不同的兜底排序。
3. **普通存档与 v2 测试档隔离**：两者有不同的存储与使用契约，不应为了减少分支混写格式或强制升级旧存档。
4. **UI 与事务内守卫**：回合归属 / 取消检查与数据库中的来源复核保护不同不变量，不能仅因都叫“检查”就删除其中一层。
5. **原回合归档重试**：保留原判断来源是合理的恢复机制；CI-07 针对重复覆盖数据，不是否定重试机制本身。
6. **预览与运行时差异**：预览不执行随机展开有明确用途，不应强制统一所有行为。

不建议借本次审查重写整个管线、引入通用插件框架，或给每个分支增加一个策略接口。

## 6. 建议的收敛顺序

1. **修复内容入口协议**：处理 CI-01；确认工坊新安装、更新和已安装数据都进入同一路由机制。
2. **统一预设解释与预处理**：将 CI-02、CI-05 一起处理，避免先补一个 fallback，再进行第二轮拆改。
3. **修复授权写入语义**：处理 CI-03，确保批量 UI 只是条目授权操作的入口，而不是第二种权限模型。
4. **统一总结入口的共享语义**：处理 CI-04、CI-06，共享请求参数投影和记录构造，但保留正常总结、补建、归档重写的真实流程差异。
5. **收敛重试持久化结构**：处理 CI-07，同时完成读取、备份、重放和清理调用方迁移。
6. **统一预算计算**：处理 CI-08，让显示与执行不再分别维护判据。

每一步应在同一次修改中迁移真实调用方并删除被替代的实现。不能只新增 helper，却继续留下原有复制逻辑。

## 8. 完成判据

修复完成后，应能逐项回答：

- 工坊生产的条目是否已经遵循消费端唯一认可的路由协议？
- 同一份预设是否只有一个格式解释与宏处理入口？
- 批量权限操作是否保持条目级授权真源，不改变无关 Agent 的权限？
- 同一总结 Agent 的配置是否在各调用入口采用相同的请求参数投影？
- 摘要记录字段是否只在一个地方构造？
- 重试覆盖信息是否从原始归档快照派生，而非维护第二份持久化真值？
- 预算诊断与实际阻断是否消费同一个判据？
- 被替代的实现、无效测试替身和旁路是否已经删除？

最终标准不是新增了多少抽象或通过了多少测试，而是下一位维护者修改同一条规则时，是否只需找到并修改一个清晰的入口。

本报告仅记录发现和建议；截至报告落笔，没有实施业务代码收敛，因此不将预期收益计为已经删除的路径。
