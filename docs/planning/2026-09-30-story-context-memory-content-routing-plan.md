  - 存储：归档记录存入 Dexie v28 `storyArchives`。第 2 区就是当前分支上有效归档排成的年表，回退时按来源消息自动退回上一节点（Q12 的实现选择）。
- 第四批已落地：

  - 第 2 区总览长度超限按裁定暂不处理。
- 第五批已落地，召回复用现有记忆召回（Q14 的实现）：

  - 编排：v2 管线先跑召回，剧情前置检查显式等它；召回失败不阻断本轮，只提示。
- 后续批次已实施摘要补建、设置/调试收口、共享 audiences 路由及 Agent 世界书配置退役；本轮接入独立 lore_select、第 3 区、依赖闭包、EJS 前可选资料预算裁剪和超限停止。最新状态与临时决定见[交付说明](../reference/story-v2-routing-delivery.md)。真实 LLM、实机与全量语义复核未执行，不提交推送。

目标：让 Story 按叙事场景组织上下文，以可回查的三层记忆延续剧情；通过开发者开关保留新旧方案。

本计划负责 Story 上下文、资料选择 Agent、三层记忆、模式开关及测试存档隔离。内容包生成、识别、条目协议、共享读取器和 Agent 世界书设置移除已独立到[内容包生成与条目路由计划](2026-10-02-content-pack-routing-compatibility-plan.md)，该计划必须保证同一份新版内容包兼容新旧两种方案。本文保留消费接口与集成依赖，不重复维护内容包实施任务。建议方案不表示已经完成实现或效果验证。

本次保留旧 Story 上下文、记忆与相关编排逻辑，通过系统设置的开发者模式分区中的独立开关启用新方案。新旧存档不做格式互转或记忆兼容；测试方案存档带永久标记，不能在非测试方案中使用。内容包按独立计划直接更新并兼容两种方案，不受测试开关控制；内容兼容不要求新旧存档互转。

D01 至 D09、D20 至 D23、D28 至 D33 的新上下文与记忆行为在测试模式生效。D24 至 D27 定义两种模式共同遵守的预设结构与按模式填充行为。D19 所依赖的共享内容层必须适配旧消费接口，也为新分区提供元数据；保留旧 Story 和记忆流程不意味着保留玩家逐 Agent 世界书权限配置。

以下为本计划建议的实施基线：

- 新模式开关默认关闭，使用新建测试档验证，不自动转换普通旧档。
- 新资料选择 Agent 使用 lore_select，采用“规则保证必选项、Agent 筛选候选、有限补充遗漏”的方式。三种模式的取舍见第 6 节。
- 短期摘要按每个正式完成回合生成，包括原文仍在 N 窗口内的回合；允许按事件分段以支持部分归档，但不强制给所有闲聊归类。
- 归档和窗口移动都保留来源原文。原文、摘要、长期记忆之间建立可回查关系。
- 第 2 区保留全部长期记忆总览，按归档节点更新；第 4 区承接窗口内原文与窗口外未归档摘要，第 5 区召回具体详情。
- 测试模式的 Story 使用专用上下文组装；旧模式继续使用原有 Delta、历史注入、摘要与召回逻辑。两条路径按模式分发，不以删除旧实现完成切换。

历史讨论基线（当前第一版实现及本轮裁定以第 16.1 节为准）：5 个不可删除分区条目的结构、顺序和按模式填充行为已确认，普通条目的消息角色、旧上下文占位符适配及既有预设补入位置仍需结合实际预设讨论；内容包、条目拆分与读取范围需进一步详细核对；每回合摘要、双层归档产物、两步召回及第 4 区与召回的关系已确认；事件关联和结束判定、物理存储、召回执行职责、两种原文粒度的使用策略与失败处理细节仍待讨论。本文既有的相关技术方案作为讨论基线保留，不因本轮确认而视为已冻结，见 Q11、Q12 及内容计划的讨论边界。

### 2.3 保持的架构边界

- 引擎实现放 src/core 的职责目录，测试放 tests 对应目录；引擎不依赖 Vue、Pinia 或 UI。
- 正式状态写入遵守 StateManager 与 per-save 写队列，UI 不直接拼装整档写入记忆状态。
- 数值计算、战斗、制作与状态结算仍由既有 Code 机制负责。
- 世界书资料、当前游戏事实、历史经历分清来源，不新增一份角色或数值状态真源。
- 主线细化、随机事件、剧情事件与任务保留现有契约。记忆归档不替代这些系统的状态结算。
- EJS 仍使用受隔离的运行时，保留现有提交权限与 AI 补丁优先级。
- 本次不引入向量数据库、通用知识图谱或新的后台自走时钟。
- 真实内容留在私有内容仓，公开引擎仓使用占位资料和合成测试样本。

### 2.4 模式开关与共享内容层

开关位于“系统设置 → 开发者模式 → Story 上下文与记忆新模式”，默认关闭并持久化到本机设置。它是独立的实验功能开关，不用现有 developerMode 诊断开关代替。仅开启开发者模式不会自动启用新方案。

| 能力                         | 开关关闭                      | 开关开启                         |
| ---------------------------- | ----------------------------- | -------------------------------- |
| Story 上下文与会话           | 旧组装、原有 Delta 和历史处理 | 本计划的分区与正文窗口           |
| 记忆写入与召回               | 旧摘要、召回及原有处理逻辑    | 三层记忆、阶段归档、原文回查     |
| lore_select 和新归档编排     | 不运行                        | 按新方案运行                     |
| 内容包生成、导入与条目元数据 | 新协议                        | 同一新协议                       |
| Agent 条目读取范围           | lore.audiences                | lore.audiences                   |
| Agent 世界书选择控件         | 删除                          | 删除                             |
| 存档使用                     | 普通存档；拒绝测试标记存档    | 测试方案存档；不自动转换普通旧档 |

把模式分发集中在管线入口，避免各模块分别读取开关后拼出混合回合。一个回合开始时确定模式，直至该回合及其后置任务结束；运行期间禁用模式切换，取消后等待任务收尾再切换。

旧模式通过内容计划的兼容适配读取同一新版内容包，保留原有上下文、记忆算法和调用顺序；默认预设与 memory_summary 输出契约不得被新方案全局覆盖。测试模式失败时使用其自身重试或报错流程，不自动降级执行旧记忆管线。

本次默认使用新建测试存档验证新方案，不提供普通旧档自动转换。开启开关但选中普通旧档时，在继续游戏前提示新建测试档或关闭开关使用旧模式。

## 3 Story 上下文结构

本节的分区填充与正文窗口行为仅在测试模式生效；预设中五个分区占位条目的存在与顺序约束在两种模式下均保留。开关关闭时占位条目展开为空，保留旧模式的 Story 组装与正文窗口语义。

### 3.1 逻辑排列

| 区域                | 内容                                                                         | 更新依据                                   |
| ------------------- | ---------------------------------------------------------------------------- | ------------------------------------------ |
| 第 1 区（固定前缀） | 固定指令、输出规范与全局必要世界资料；普通预设条目可按作者安排穿插在分区之间 | 预设或内容包配置发生变化                   |
| 第 2 区             | 全部长期记忆总览：事件总结与已结束事件记录，类似历史年表                     | 新事件结束并归档时更新；回退时恢复归档节点 |
| 第 3 区             | 本地势力、本地地理、必要文化与区域规则                                       | 活动区域或对应资料发生变化                 |
| 第 4 区前半         | 正文窗口外、尚未归档的摘要，按时间排列                                       | 窗口移动、摘要完成、事件归档               |
| 第 4 区后半         | 最近 N 个完整回合，保留玩家与 Story 的消息顺序                               | 正式回合追加或回退                         |
| 第 5 区             | 本轮人物与话题资料、召回记忆、原文细节、当前事实、剧情要求                   | 每轮重建                                   |
| 最末                | 本轮玩家输入                                                                 | 每轮变化                                   |

上述编号为逻辑分区，对应预设中的 5 个不可删除占位条目，其相对顺序固定为 1→5，允许在中间插入普通条目。不要求每一区对应一条 API 消息；装配时在占位位置加入该区已组装好的消息列表，例如第 4 区保留真实 user／assistant 历史角色，不能将五区整体重新压成单条 system 文本。固定规则使用系统层；第 5 区与玩家输入可按现有协议能力组成末尾 user 消息，以清晰边界区分引擎参考资料和玩家原话。普通条目如何映射消息角色，以及旧上下文占位符如何适配仍待 Q11 讨论。

实现时检查 OpenAI Chat、Claude Messages 与 Gemini 的实际序列化结果。当前项目后两者的适配器限制会话中途的 system 消息，不能只调整应用层数组顺序就假定尾部资料位置已经正确。

第 2 区提供当前有效分支的全部长期记忆总览，不按本轮话题筛成相关事件列表。正文是概括性的事件总结与已结束事件记录，形式类似历史年表；正常推进时仅在新事件结束并触发归档后更新。关系、承诺或事实变得重要本身不单独触发这一层更新。回退按第 11.4 节恢复到对应归档节点，属于历史状态恢复。

已确认归档同时产生事件详细记录与纳入长期总览的概括记录；两者是不同详略的逻辑产物，不预先要求两次模型调用或两张独立数据表。具体生成实现、物理存储、总览长度处理和归档节点保存方式仍待讨论（Q12）。

### 3.1.1 预设分区占位条目与双模式装配

5 个占位条目是预设结构的一部分，在实验模式关闭时也保留。用户不能删除它们或改变其 1→5 的相对顺序；可以在分区之间插入普通预设条目，继续编写叙事指令、文风要求和输出约束。例如：

```text
第 1 区占位条目
普通预设条目 A
第 2 区占位条目
第 3 区占位条目
普通预设条目 B
第 4 区占位条目
第 5 区占位条目
```

- 实验模式开启：引擎分别组装五区消息，遍历预设条目时在各占位位置加入对应消息；保留普通条目的穿插位置，不统一搬到顶部。
- 实验模式关闭：五区占位条目展开为空，不生成空白消息，也不触发新分区的资料选择或记忆任务；其余条目和旧上下文仍沿原有路径装配。
- 旧预设中的历史、世界书、记忆等上下文占位符不得全局删除或停用，旧模式继续使用。实验模式需适配这些旧入口，避免与五区重复注入；具体映射待 Q11 核对，不通过删除其周围的普通指令实现适配。
- 分区条目插入的是已组装消息，不只是向旧的单条 system 字符串追加文本。5 个分区不要求最终请求恰好有 5 条消息。
- 预设创建、导入、更新、重置与编辑流程均需维持五区条目存在和顺序约束；稳定标识、缺失条目的补入位置及普通条目的协议映射在 P0 与内容计划 C0 对齐，不在此预设具体字段或自动迁移算法。

上述旧入口的重复注入处理不改变第 2 区概括与第 5 区详情暂不去重的规则。

### 3.2 正文窗口的唯一口径

N 必须为正整数（N>0），不允许 N=0。N 表示最近 N 个正式完成的玩家输入与 Story 正文回合，不能直接用任意消息总数除以二代替。系统卡片、侧链输出、调试消息、失败草稿和本轮尚未完成的输入不增加完整回合数。

设 W 为最近 N 个有效完整回合，S 为有效短期摘要片段集合，A 为已被有效归档覆盖的片段：

```text
第 4 区摘要 = 来源位于 W 之前、且不属于 A 的 S
第 4 区原文 = W 中的完整输入与正文
第 4 区顺序 = 摘要按来源时间排序，然后原文按回合排序
```

约束：

1. 窗口内内容不重复注入摘要，即使该回合已生成摘要。
2. 窗口外未归档摘要全部显示，不设 M、Top K、按重要度淘汰或隐含时间上限。
3. 窗口内原文即使已被归档，也保留到其自然移出 N 窗口。
4. 一段摘要不应跨越窗口边界而无法拆分。按回合生成并建立来源关系可避免此问题。
5. N 的设置只有一个真源。复用还是替换 Story 的 historyLayers 在协议批次确定，不能同时保留两个互相覆盖的窗口旋钮。
6. 其他 Agent 的历史层数不自动改成 Story 的 N。

例：完成第 30 回合，N 为 4，第 1 至 18 回合涉及的内容已全部归档，第 19 至 26 回合未归档。第 4 区显示第 19 至 26 回合摘要和第 27 至 30 回合原文。若第 12 回合还存在未归档片段，该片段也必须显示。

### 3.3 第 3 区的更新

第 3 区采用偏地理区域的定义，是当前活动区域的背景集合，不扩展为所有变化缓慢的资料。由内容包声明适用范围，代码根据当前位置与既有场景事实定位，避免每轮让 Agent 任意重写相同资料。

触发重新选择或构建的情况：

- 位置跨出当前资料的适用区域。
- 对应条目、内容包、依赖或启用状态发生变化。
- 原选取结果不再满足新的条目规则。

仅谈及异地不会自动替换本地区背景；异地相关资料进入第 5 区。国家、城市、城区的层级按内容声明处理，不将分类标签直接当作地理实体，也不沿父链展开每一层全文。

位置命中口径（2026-10-10 裁定放宽）：`activation.locations` 与玩家位置路径按**包含**判定——玩家路径的任一层级包含声明字串即命中，而不是反向包含或要求层级逐字相等。原逐字相等判定会在国名被并入更长路径段时失效。唯一实现文件为 `src/core/content/lore-selection.ts`；第 3 区区域命中与本轮候选的位置判定必须共用同一函数，不能只放宽其中一处。`regionSnapshotKey` 仍由区域路径、最终区域条目正文及路由元数据生成；此次只调整位置匹配，不改快照键的生成口径，相同路径和相同区域条目结果仍保持稳定。本轮不做地名归一或地点树父链上溯；声明侧仍建议使用完整势力名，并保留别名与 `keywords` 兜底，包含命中不能解决「模型只写城市名」的情况。代码已按此裁定实施：区域命中与候选判定共用包含匹配，空声明不命中，不跨路径层级拼接匹配。

### 3.4 第 5 区与当前事实

第 5 区包括本轮选择的条目正文、相关短期或长期记忆、按需读取的原文、当前状态投影，以及现有剧情系统提供的可用导演信息。第 2 区提供概括，第 5 区召回具体详情；暂不对第 2 区与第 5 区做去重，不因总览已提及事件而排除其详情。

当前 HP、位置、游戏时间、任务状态等以引擎状态为准。人物背景来自世界书；玩家与人物的经历来自记忆；原始设定中描述的活动地点不覆盖存档里已经发生的迁移。

第 2、3、5 区的注入文本独立于正式对话存储。可以在调试记录中保存每轮快照，但不能把注入资料写进 ChatMessage 后再作为永久历史重复发送。

### 3.5 缓存与预算

固定前缀保持字节和排序稳定；第 2 区沿用当前归档节点的长期总览，归档或回退时更新对应内容；第 3 区在适用范围不变时复用构建结果；第 5 区每轮替换。正文窗口移动、区域变更和归档改变第 4 区时，允许后续前缀失效，不以保留缓存为理由保留失效资料。

预算分开统计固定资料、长期总览、区域资料、摘要、原文、本轮资料、召回片段和输出预留。长期总览的长度及超限处理需后续讨论，不能自行改为本轮相关事件筛选。优先减少可选资料与可选召回片段。

全部未归档摘要属于已确认规则。若保留这些摘要和 N 个完整回合后仍超出模型可用窗口，必须明确报告超限及分区用量，允许用户在 N>0 范围内调整 N 或使用更大窗口；不能偷偷增加 M、截断正文、伪造事件完成或按数量强制归档。

## 4 内容包消费接口

条目模型、稳定身份、audiences、分类拆分和公共读取器由[内容包生成与条目路由计划](2026-10-02-content-pack-routing-compatibility-plan.md)第 3 至 5 节统一定义，本计划只消费其结果。

- 新 Story 接收固定、区域和本轮候选，以及稳定条目引用、正文、依赖和选择依据。
- 旧 Story 通过同一内容层的兼容适配继续使用原有资料展开、预设和占位符，不依赖 lore_select。
- 新旧模式的读取范围一致，旧 worldBookIds 不再决定权限；具体控件与配置清理由内容计划实施。
- 条目读取范围按每个条目自身的 audiences 判定，不按分类或类别批量决定；分类只作为内容端的组织与初始建议。
- 内容更新只使相关资料缓存失效，不改写历史、记忆格式或测试档标记。

## 5 激活规则的 Story 消费约定

规则声明、构建校验和公共判定见[内容包生成与条目路由计划](2026-10-02-content-pack-routing-compatibility-plan.md)第 4 节；新模式负责以下消费行为：

1. 固定资料进入顶部；当前场景的必需约束和背景不能被选择器删除。
2. 宽松匹配生成候选，由第 6 节选择 Agent 筛选并有限补充。
3. 硬性禁用、audiences 不匹配和硬排除不能由依赖或补充绕过。
4. 本地资料归入第 3 区，本轮人物和话题资料归入第 5 区；激活不代表安排人物登场或触发事件。
5. 旧方案保留其确定性读取和展开方式，新分区和筛选规则不能成为其运行前提。
6. 第 3 区的位置命中按**包含**判定（2026-10-10 裁定放宽，见第 3.3 节）；区域命中与候选判定共用同一位置匹配函数；权限、停用、硬排除、依赖闭包与 `regionSnapshotKey` 口径不变。

共享内容协议先交付，选择器编排和分区效果由本计划验收。

## 6 资料选择 Agent

### 6.1 三种行为的取舍

| 模式 | 行为                                             | 主要限制                   |
| ---- | ------------------------------------------------ | -------------------------- |
| 主导 | Agent 主动寻找并决定大部分资料，规则补充必要内容 | 检索成本和遗漏风险较高     |
| 筛选 | 宽松规则提供候选，Agent 删除不相关候选           | 难以发现候选池外的遗漏     |
| 补充 | 规则决定注入内容，Agent 查找遗漏                 | 无法消除规则本身造成的冗余 |

建议第一版实现一个 lore_select，组合筛选与有限补充。无需为三种模式分别增加三个 Agent。是否对内容作者暴露模式切换列入 Q02，默认不新增玩家配置复杂度。

### 6.2 输入与输出

输入使用当前场景事实、近期对话、玩家输入、必要的召回信息，以及候选目录。目录包含条目引用、名称、简介、关联主体、大小和选择依据；不先发送所有正文。

Agent 输出保留的候选引用、补充检索需求及简短理由。代码校验引用，再读取正文。理由进入调试记录，不占用 Story 的资料正文区。

lore_select 本身也遵守 audiences。其可检查集合应与 Story 可用集合相交；生成端显式声明选择器需要的读取范围，不能赋予不受约束的全库读取再转交 Story。

### 6.3 运行约束

- 区域背景变化时重新选择第 3 区；其余轮次复用有效选择。
- 每轮为第 5 区筛选与补充；没有需要判断的候选时可跳过调用。
- 限定补充轮数、候选规模和读取正文量，具体数值用语料评测确定。
- 失败时保留必选项及规则排序后的预算内候选；取消时停止后续检索与 Story 调用。
- 选择器不创作剧情，不提交状态补丁，不调用带副作用的世界书求值路径。

## 7 三层记忆与原文来源

每个正式完成回合生成摘要、归档产生详细与概括两层结果，以及第 4 区与召回的关系已经确认。以下区分保存内容和本轮注入内容；具体物理记录结构、执行职责及失败处理仍作为待讨论事项（Q12 至 Q15）。

### 7.1 存储职责

| 层       | 保存内容                                                                                             | 生命周期                           | 上下文位置                                                     |
| -------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------- | -------------------------------------------------------------- |
| 现状     | 正式玩家输入与 Story 正文                                                                            | 原文持久保留                       | 最近 N 回合在第 4 区                                           |
| 短期摘要 | 已发生行为、关键对白含义、结果、关系变化、未完事项                                                   | 保存来源；未归档片段按窗口规则常驻 | 第 4 区或按需展开到第 5 区                                     |
| 长期归档 | 事件详细记录：起因、经过、结局、重要约定、持续影响与来源关联；概括记录：事件在长期经历中的位置与结果 | 随存档保留，可回查原文             | 概括记录纳入第 2 区全部长期总览，详细记录及原文按需进入第 5 区 |

messages 表继续作为原始对话真源。不要为“现状”复制一份正文到新表，也不要把资料注入、推理内容和检索日志混进原文。

测试模式的记录应明确区分短期摘要与长期归档，并按测试存档隔离。可以扩展现有 memories 表或采用必要的新表，具体在 P0 决定；旧模式继续读写原有记忆形状，不迁移其记录，也不让旧读取器处理测试记录。

### 7.2 短期摘要

每个正式完成回合生成摘要，即使该回合原文仍在 N 窗口内。同一回合涉及多个事件时允许分段，不强制把所有闲聊都归入某个事件。摘要及其片段关联对应的来源回合与消息；内部引用由代码绑定。

摘要生成与注入分开：原文仍在 N 窗口内时，第 4 区只注入完整原文，不重复注入摘要；原文移出窗口后，已有的有效未归档摘要立即承接。

摘要保留实际行动与结果、约定和信息、关系变化及原因、仍未解决的事项。计划、猜测、传闻和已经证实的事实保持语义区分。未实际演绎的剧情计划、未揭示真相和世界书全文不能被总结成玩家已经经历的事件。

不沿用固定最低字数驱动内容的方式。短回合允许短摘要，验收依据是信息完整与忠于来源。

必要的语义信息包括：

| 信息                      | 责任                                 |
| ------------------------- | ------------------------------------ |
| 摘要正文与事件分段        | AI 提取，引用已发生的叙事            |
| 来源消息、回合与版本      | 代码绑定并校验                       |
| 存档、物理 ID、真实时间戳 | 代码生成                             |
| 游戏时间范围              | 优先读取回合事实；无法确定时保留未知 |
| 人物、地点和主题          | 从摘要提取并按现有实体名规范归一     |
| 有效性与归档覆盖          | 代码根据来源及有效归档计算           |

窗口外某回合的摘要尚未成功生成时，不允许静默遗漏该段历史。建议在下一轮组装前补齐缺口；失败则明确提示该缺口，保留原文和重试入口。具体交互在 P4 确定，不悄悄用旧摘要冒充。

### 7.3 原文定位

回查以明确的消息关联为主，回合序号用于排序与展示。重生成、导入和同回合多版本下，不能仅凭 turn 或现实时间戳认定来源相同。

为引用保存足够的来源修订信息，能够识别正文已被编辑或替换。摘要与归档失效时保留可诊断原因；重新生成后绑定当前有效版本。

测试记录从生成时就绑定来源。旧模式记忆继续由旧逻辑处理，本次不补建其来源，也不把旧摘要转换为新模式记录。

## 8 阶段性事件归档

### 8.1 触发语义

归档以事件结束为触发条件，包括成功完成、放弃和失败；这一口径已确认（Q03 已关闭）。新事件结束并触发归档时，第 2 区更新全部长期记忆总览，保留此前有效历史并纳入本次事件概括。

回合数量、记忆条数、跨日、普通转场、摘要过长或模型窗口不足都不构成事件结束证据。事件可以跨多个地点和较长时间，未结束时摘要继续按规则保留。

归档同时产生两个层次的结果：

| 产物            | 内容与用途                                                                                     |
| --------------- | ---------------------------------------------------------------------------------------------- |
| 事件详细记录    | 记录为什么开始、关键经过、怎样结束、重要约定与持续影响，并关联来源原文；供后续检索和详情读取。 |
| 第 2 区概括记录 | 用较短文字记下事件在长期经历中的位置与结果，纳入全部长期记忆总览。                             |

例如，第 2 区可记为“在北城调查失踪案，最终因线索中断放弃调查，与当地守卫留下合作关系”。事件详细记录则保留调查地点、线索提供者、放弃原因，以及守卫具体答应的事情，并能回查对应原文。

事件名称、时间地点、参与人物和来源范围可作为详细记录的组织信息，具体字段待存储契约讨论。结局明确但仍有后续影响时，可以归档已结束阶段，并保留尚待处理的后果。

归档成功后，仅被有效覆盖的短期摘要退出常驻范围；原摘要、事件详细记录和原文继续保留并可检索。未结束的其他事件仍在短期记忆中，窗口内原文不因归档提前退出。

### 8.2 归档生成过程

以下流程落实已确认的双层归档产物；事件关联、结束判定职责、模型调用和存储实现仍需讨论。归档失败时不提前移除摘要的行为边界保持不变。

1. 记忆 Agent 从正式剧情中提出阶段收束判断和证据。
2. 代码定位相关短期摘要片段与来源消息。
3. 使用摘要组织事件经过，对约定、关键转折和结局回查必要原文。
4. 生成事件详细记录与第 2 区概括记录草稿，校验来源仍属于当前有效分支；两层产物不等于必须分别调用模型。
5. 归档生效时保存事件详细记录，将概括记录纳入第 2 区长期总览，并保留可恢复的归档节点；具体生成实现和保存方式在 Q12 中确定。
6. 长期记忆、覆盖关系和对应总览节点保持一致；下一次组装时，只让被有效归档完整覆盖的摘要片段退出第 4 区常驻摘要范围。

归档失败时，第 2 区保持上一有效归档节点的总览，短期摘要保持未归档；不能先移除摘要再等待长期记忆生成。生成调用在写锁外进行，事务只负责最终校验和写入。

### 8.3 多事件与部分归档

一回合可能同时包含已经完成的委托和仍在发展的关系事件。归档委托后，关系事件的摘要仍须保留。

建议以“回合摘要中的事件片段”为最小覆盖单元。长期记忆引用被覆盖片段，片段是否归档由有效引用派生；避免在整条摘要上使用一个 archived 布尔值而丢失未完内容。

同一片段可作为多个事件的背景证据，但只有被明确完整承接后才退出未归档集合。共同背景引用不应误判为对所有内容的覆盖。

### 8.4 归档与游戏系统的边界

记忆归档记录已经发生的事情，不直接完成任务、推进主线、创建奖励或改变人物状态。主线细化和任务系统产生的结果可以成为归档证据；归档本身不写这些系统的状态。

第一版优先复用 memory_summary Agent 完成摘要和收束判断，归档作为需要时才运行的工作模式。是否独立配置归档模型见 Q04。

## 9 记忆召回与具体内容展开

召回目的、先定位再读详情的两步流程、两种原文读取粒度及第 4 区与召回的关系已确认。第 2 区展示全部长期记忆概括，第 5 区提供具体详情，暂不做两区之间的去重。检索执行者已裁定为复用现有召回（Q14）：LLM 模式由召回 Agent 按编号选候选，Embedding 模式由向量核排序；详情与原文由代码展开，选中即附原文。原文读取决策的细化和粒度的默认策略仍待测试后讨论。

### 9.1 召回范围

召回用于补充本轮需要、但常驻上下文没有充分提供的具体信息，不是再生成一份常驻前情总结。允许检索短期摘要（含保留的已归档来源摘要）、事件详细记录及其来源原文。查询依据包括本轮玩家输入、场景、人物和近期对话；不能只依靠一句“继续”生成查询。

保留现有显式 LLM 或 Embedding 选择与可选重排能力作为实现基线。Embedding 可帮助定位语义相关候选，但不能替代事件确认与来源原文读取；具体检索组合及执行职责仍待讨论。向量空间隔离、失败诊断、候选数量和远端费用约束沿用既有机制，不自动全库重嵌入。

### 9.2 两级读取

```text
本轮输入、场景、人物与近期对话
  → 第一步：检索摘要或事件详细记录，定位相关经历
  → 第二步：读取所需详情；需要准确措辞、约定、数字或关键因果时展开来源原文
  → 原文方案 A：完整的玩家输入与 Story 回合
    或方案 B：相关原文片段加必要前后文
  → 标注来源，提供实际正文
  → 第 5 区
```

一般背景可以提供事件详细记录；需要核对精确措辞、约定、数字和关键因果时回查原文，不能把模型重述当作引用。原文缺失时明确标示只能提供摘要。

最终传给 Story 的是摘要正文、归档正文或具体原文，不是只有 ID、分数与召回理由的列表。

原文召回的两种方案均纳入实施与测试，不在本轮二选一：

| 方案         | 读取内容                        | 测试关注点                                          |
| ------------ | ------------------------------- | --------------------------------------------------- |
| 完整回合     | 对应的完整玩家输入与 Story 正文 | 是否保留充分语境，以及请求大小、延迟和 token 消耗。 |
| 片段加前后文 | 相关原文片段及必要上下文        | 片段边界是否遗漏指代、条件或因果，以及节省的消耗。  |

用相同查询、同一有效来源比较信息完整性、精确性、叙事效果和消耗，再决定默认或选择策略。本轮不预先增加玩家开关，也不确定由模型自动选择。具体片段边界与前后文范围随测试细化。

### 9.3 第 4 区与召回的关系

第 4 区窗口外未归档摘要全量常驻，不经过召回相关性筛选。召回可以沿摘要读取更早的原文，也可以沿第 2 区所概括的事件读取详细记录及原文，补入第 5 区。

例如，第 4 区摘要记着“玩家答应三天后归还物品”；本轮核对是否违约时，召回来源原文中的时间、物品和约定条件。摘要维持连续性，召回补足具体细节。

一次召回不改变记忆的归档状态，不改变第 4 区摘要范围，也不让旧原文重新占用最近 N 轮的名额。第 5 区可按本轮需求控制大小；第 2 区概括与第 5 区详情暂不去重。与窗口内原文重复时的具体处理规则仍待细化，但不得因此改变已确认的常驻范围。

### 9.4 权限与隔离

所有查询和原文展开限定当前存档与有效分支。角色未获知的信息不能因为检索到了幕后资料就被改写为已知经历。

第一版由 Story 前的召回流程完成原文展开。是否让 Story 在生成途中通过只读工具主动回查，列为 Q05，不作为本次第一阶段的必需依赖。

## 10 运行时编排与写入

以下流程仅在测试模式且存档模式匹配时执行。模式校验在加载、自动恢复、继续、重新生成等入口共用，并早于上下文构建、LLM 请求与状态写入。

### 10.1 Story 调用前

1. 捕获本轮可用的存档状态、正式历史、玩家输入与取消信号。
2. 读取当前有效归档节点的第 2 区长期总览，不每轮重新生成；根据 N>0 计算第 4 区，并检查来源和摘要覆盖是否完整。
3. 确定条目读取范围，复用或重建第 3 区，生成本轮候选。
4. 召回相关记忆并按需展开原文。
5. 按既有剧情契约运行前置剧情逻辑。若它使用本轮召回，显式建立依赖，不能让两者无依赖并行后读到空输出。
6. lore_select 完成本轮候选筛选与补充。对剧情前置输出只接收其被允许使用的投影，不通过选择过程泄露幕后动机。
7. 对最终选中条目执行一次受控渲染，组装各分区并调用 Story。

候选计算和独立检索可以并行；实际依赖以消费数据为依据。不要为了并行而使 Agent 读到上一轮结果。

### 10.2 Story 调用后

正式正文产出后，摘要草稿生成可以与既有调度器等后置工作并行。摘要落库与归档生效必须等待对应回合被正式接纳，并校验分支没有变化。

当前 plot_post_check 依赖 memory_summary 输出。应区分“已生成的摘要草稿”和“已提交的摘要记录”：后置 Agent 可以使用本轮草稿，但不能形成“摘要落库等后置完成，后置又等摘要落库”的循环。

失败重试、取消和重生成不会为同一个有效来源重复建立记忆。网络调用不占用存档写队列；最终写入通过 StateManager 管线或经确认的命名入口接入同一 per-save 队列。

### 10.3 EJS 与会话缓存

选资料阶段不提交 EJS 写入。最终 Story 渲染使用显式 runtime 和同轮快照，一轮同一条目的求值不因预算估算、预览和正式组装重复发生。

保留 EJS 草稿、AI vars_update 后落、冲突时 AI 胜出的规则。选择器或其他 Agent 的只读求值不得改变 Story 后续看到的状态。

旧模式保留 promptSessions 与 Delta 路径，测试模式不读取或追加旧 Story transcript。缓存按存档和必要的模式签名隔离，切换时清理当前不适用的运行时句柄，不全局删除普通存档的旧会话。

两种模式均读取直接覆盖后的内容包；内容元数据或有效条目变化时，按各自缓存规则使对应请求缓存失效。其他 Agent 同样不能绕过新的 audiences 读取限制。

## 11 测试存档隔离与内容接口

### 11.1 共享内容兼容

内容包安装、更新、拆分引用映射及双方案兼容归[内容包生成与条目路由计划](2026-10-02-content-pack-routing-compatibility-plan.md)。同一包在两种模式中读取相同身份与正文，旧消费方式通过适配继续有效。

内容拆分若影响存档中的内容启用引用，可以按内容计划做引用映射；这不构成历史消息或记忆格式转换，也不得改动测试标记。“存档不做跨方案兼容”不能用来免除新版内容对普通档的兼容。

### 11.2 Agent 配置边界

Agent 世界书配置的移除、默认内容、重置与更新入口由内容计划统一处理。Story 计划只负责按本轮模式选用相应预设与摘要契约，保留旧模式所需配置；不得将新摘要输出直接交给旧处理器。

### 11.3 测试存档标记与准入

采用 metadata.storyContextV2 标记测试方案存档，与同目录的实验模式实施说明保持一致。该标记由代码写入，独立于本机开关持久存在，不能由切换设置、重置 Agent 配置或回退快照清除。

- 新建测试档时写入标记；任何新方案的生成或记忆写入发生前，存档必须已经具有标记。
- 开关关闭时，存档列表可以显示测试档及其标识，但载入、自动恢复、继续和重生成都必须拒绝使用，提示开启测试方案。
- 当前载入的是测试档时关闭开关，结束当前载入状态并返回存档选择；保留存档数据，不让同一会话继续执行旧模式。
- 重新打开开关后，可继续使用该测试档。
- 普通旧档没有标记，继续由旧模式使用；本次不提供旧档转换、旧摘要迁移、历史批量补建或测试档降级。
- 数据库可以新增保存测试记录所需的表或字段，但这不意味着需要升级旧档的语义内容。

测试档回退到其较早快照仍是测试档。恢复操作不得用快照中的旧 metadata 覆盖并消除测试标记。

### 11.4 回退与重生成

测试模式恢复快照时，按恢复后的正式消息集合校验摘要来源和归档来源；旧模式保留其原有恢复流程：

- 回退到某次归档之前时，第 2 区恢复到恢复点之前的上一个有效归档节点；不保留被撤销归档的总览内容。若此前尚无归档，则恢复为尚无归档总览的状态。
- 来源仍有效的记忆保留。
- 来源被替换或不在恢复分支的摘要不参与上下文。
- 失效归档不再覆盖其引用片段；恢复点仍有效、且未被其他有效归档承接的正文与摘要恢复未归档语义，并按既有 N 窗口规则展示；不恢复被回退移除的未来消息。
- 不能只比较现实 createdAt 或 turn；同回合重生成可能具有不同正文。
- 回退后的 pending 网络响应在最终写入前检查来源版本，不能把被放弃分支的记忆写回来。

具体采用快照携带记忆关系、保存总览节点还是可重建关系，留待后续记忆讨论并在 P0 确定；必须满足上述可逆语义，并始终保留测试档标记。本节是测试档内部一致性，不要求新旧存档互相兼容。

### 11.5 导出与删除

FullBackup、单存档导出导入、删档级联覆盖测试标记及新增记录关系。导入重发内部 ID 时，来源消息引用与摘要、归档引用同步重映射，测试标记保持不变。

关闭测试开关时可以保留或导入测试档作为存储数据，但不得自动载入或继续运行。重新导入、复制或导出再导入不能将测试档变成普通档。普通档仍沿用已有导入导出逻辑，本次不要求不同记忆格式互转。

区域资料选择缓存、Story 组装缓存和向量索引按可重建数据处理；用户经历及长期记忆不能随内容包更新或包版本变化清空。

## 12 前端与调试

### 12.1 设置页面

在 DeveloperSection 中新增独立的“Story 上下文与记忆新模式”开关，默认关闭。说明文案应告知新旧逻辑并存、测试档只能在新模式下使用、内容包更新不会随开关回退。设置关闭时执行第 11.3 节的测试档退出与准入规则。

Agent 世界书设置移除与只读来源说明归[内容包生成与条目路由计划](2026-10-02-content-pack-routing-compatibility-plan.md)，两种模式共同生效。

测试模式只提供一个正整数 Story 正文窗口 N（N>0），设置与运行时均不接受 N=0，不增加摘要 M，也不读取 memoryCompressionThreshold 触发归档。旧模式需要的记忆设置及数量处理逻辑继续保留，按模式显示相应说明，不因测试方案接入而删除。

召回模式、Embedding 源、重排等设置与窗口规则分开。快照数量属于快照管理，不能与记忆归档阈值混用。

### 12.2 记忆查看

测试模式下在既有 MemoryPanel 上展示长期总览及其归档节点、短期摘要、归档事件、来源回合和原文回查。显示已归档覆盖和未归档片段，避免用户把“退出上下文”理解成原文删除；普通存档保留旧记忆展示。存档列表与详情显示测试方案标记，不能只靠临时页面状态判断。

自动归档判断需要能够解释结局证据；是否增加手动纠正入口在 Q08 决定。

### 12.3 调试证据

旧模式保留现有调试行为；测试模式的每个正式 Story 调用能够查看：

- 本轮实际运行模式与存档测试标记。

- 各上下文区的实际内容、条目引用和大致用量。
- 条目因 audiences 被排除、规则必选、规则候选、Agent 筛选或补充而进入的原因。
- 第 2 区全部长期记忆总览、对应归档节点及更新或回退原因。
- 第 3 区沿用或重建的原因。
- 第 4 区的 N、原文回合、摘要来源和归档覆盖。
- 第 5 区召回正文及展开的原文来源。
- 归档事件、收束证据、覆盖片段和失败诊断。

调试日志不携带 API Key；依照既有调试历史保留策略控制体积，不把完整调试请求加入日常存档备份。

## 17 完成标准

本重构完成时，应同时满足：

1. 内容计划已提供共享协议、旧消费适配与新方案接口，同一包支持两种方案。
2. Story 的预设、占位符、资料读取与摘要输出正确消费对应模式契约，且不绕过共享 audiences。
3. 系统设置的开发者模式中提供默认关闭的新模式开关；旧 Story、记忆和 Delta 逻辑保留，单轮模式固定。
4. 预设强制保留五个不可删除占位条目，相对顺序为 1→5，允许在中间插入普通条目。测试 Story 在对应位置加入第 1 区固定内容、第 2 区全部长期总览、第 3 区地理区域背景、第 4 区、第 5 区及末尾当前输入，并能在刷新后恢复同一有效内容；旧模式下五区条目展开为空，旧上下文仍按原有方式装配。
5. 测试模式只配置正整数正文 N（N>0），不允许 N=0；窗口内完整原文，窗口外未归档摘要全量显示且无重复注入。
6. 测试模式在事件结束时归档，包括成功完成、放弃和失败，同时生成事件详细记录与纳入第 2 区全部长期总览的概括记录；保留原摘要及原文，部分归档不丢失其他未完内容。第 5 区按先定位后读详情的流程召回，完整回合与片段加前后文两种原文方案均有测试记录；召回不改变归档状态、第 4 区范围或 N 轮名额，暂不做第 2 区与第 5 区之间的去重。
7. 测试标记随存档永久保留；关闭新模式不能载入、恢复或继续测试档，不提供旧档转换、历史记忆迁移或测试档降级。
8. 测试档内部回退、重生成、切档、导入导出、重复导入与内容更新后，来源、覆盖关系及长期总览节点仍正确；回退归档时，第 2 区恢复上一有效节点，仍有效的相关正文与摘要恢复未归档语义。
9. 使用内容计划的同一包通过两种方案回归；开关不改变条目读取范围、不切换包版本，也不恢复 Agent 世界书配置。
10. 针对性测试、旧模式回归、完整本地闸门、真实内容包契约及真实回合验收分别有记录。
