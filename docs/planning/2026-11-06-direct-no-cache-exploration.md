# 无缓存直出：功能取舍探索

状态：**探索草案，未裁定、未实现**。日期：2026-11-06。

本轮讨论最基本的无缓存直出：用户希望先看各功能合并或放弃的具体代价，再决定取舍。以下区分已存在的代码能力、据此作出的可行性判断和候选建议；不确定删除清单，不定义正式输出 schema，也不安排实施步骤。

## 1. 已确定的约束

- 每楼 **1 次主 AI 请求**，最多再有 **1 次前置记忆回溯请求**；回溯不需要时省略。
- 请求次数是实际模型请求次数，不是 Agent 名称数。工具结果回传、格式修复、摘要补建和自动重试都可能再发请求，不能藏在“一次主调用”里。
- 不使用 Delta 会话优化，每轮可以发送完整所需上下文；这不等于能够禁止服务商自行缓存相同前缀。
- 本地解析、检索、计算、状态提交和界面更新不消耗模型请求，可以继续使用。
- 现有功能可以合并或放弃，但本轮尚未决定具体取舍；调用预算不因保留某项功能而放宽。

现有普通 chat 与工具循环均可能重试，v2 回溯还有单独的格式重试，不能直接沿用为严格次数保证。见 `src/core/agents/agent-client.ts:222`、`:285`、`:502`，`src/core/agents/agent-orchestrator.ts:1407`。

## 2. 各功能合并与放弃的具体代价

表中的“可合并”指已有解析／执行基础使其具有可行性，**不代表现有主回复已经接通，也不代表真实模型质量已经验证**。

| ------------------------------------------------ | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| 正文、选项、角色叙事档案与编年史                 | 正文已经同次输出并解析这些内容；可继续保留                                | 没有选择按钮、角色资料不更新，或经历无法累积，取决于删去哪部分                 | 新人物的档案／经历仍依赖实体存在，不能只留下更新标签                                             |

## 3. 不能靠简单合并提示词跨过的约束

### 主 AI 当前拿到的资料不足以接管全部数值工作

Story 的 `CHARACTER_STATE` 默认使用 NARRATIVE 视图：只保留主角／在场者，省略装备精确 stats、技能 cost／cooldown 和物品 stats。HP／MP／SP、金币和物品数量虽可见，却不能据此推断所有效果。见 `src/core/prompts/placeholder-registry.ts:737`，`src/core/prompts/context-visibility.ts:77`、`:386`、`:443`、`:468`、`:486`、`:503`。

因此，主回复承担哪些职责，就需要为这些职责重新选择充分的信息。把其它 Agent 的整套提示词拼到 Story 后面，不会自动补齐被过滤的字段，也不会改变世界书的 audiences 权限。当前内容包及用户预设还可能覆盖默认配置；本轮没有读取浏览器中的有效设置。

### 三套后处理的输出不能直接相加

- 时间推进有顺序：全局变量提交后推进时钟，再同步地图在途状态。见 `src/core/agents/agent-orchestrator.ts:1847`。
- daily 当前排在 vars 前，避免本轮新施加的状态立刻扣掉整轮时间。见 `src/core/types/types.ts:609`。
- 药物库存只归 vars 扣除，daily 处理效果；主回复合并后仍必须避免一瓶药扣两次。见 `src/core/variables/daily-check-translator.ts:36`，`src/core/variables/vars-update-translator.ts:445`。
- 同一字段同时给最终值和增量，或 daily 与 vars 同时声明一次治疗，会被顺序执行，而非自动识别成同一事实。见 `src/core/variables/vars-update-translator.ts:223`、`:284`。
- 同名状态 add 会叠层或刷新时长，不是自动去重。见 `src/core/state/state-manager.ts:1313`。

这些大多是本地执行顺序和声明所有权的要求，**并不强制要求多个模型调用**。但若只把现有输出拼在一起，已有语义冲突仍然存在。

### 新人物不能只关闭 entity_gen

现有 `<character_updates>` 只承载叙事档案与经历，不含完整数值实体。管线发现未知人物后会自动调用已有生成链，完成实体后才提交角色更新。见 `src/core/character/character-updates.ts:8`、`:93`，`src/ui/lib/game-pipeline.ts:859`、`:909`。

若仅切断生成调用，按名更新找不到人物会失败，不能把这种情况当作已经实现“轻量新 NPC”。已有实体 parser 与组装逻辑可复用，是合并的基础；是否让主回复承担完整实体输出，仍是待选取舍。见 `src/core/state/state-manager.ts:911`，`src/core/agents/entity-gen-parse.ts:521`，`src/core/agents/entity-gen-agent.ts:604`。

同样，`characters.add.inventory` 当前只取名字、描述、数量、类型、品质和装备槽等少量字段，不保留完整 stats／effects，不能作为完整新装备／技能生成的替代。见 `src/core/variables/vars-update-translator.ts:361`。

### 本地数值规则仍有保留价值

状态层已有资源加减与钳制、库存检查、同名状态叠层、经验升级、FP 账务和按存档写锁。主 AI 声明发生的变化，不意味着这些规则也交给它重算。见 `src/core/state/state-manager.ts:604`、`:640`、`:1096`、`:1159`、`:1244`、`:1460`。

当前 AI 补丁为逐项 best-effort 提交：某项失败不会撤销其它成功项。一份主回复不自动等于整楼原子事务，也不自动保证正文与所有结算均成功。见 `src/core/state/state-manager.ts:634`、`:659`、`:666`。

## 4. 可供选择的取舍方向

以下只是比较后的候选，**不是已经决定要保留或删除的功能清单**。

1. **优先探索合并常规后处理、摘要和实体输出。** 这些已有解析与本地执行能力，能减少独立调用，同时有机会保留基础 RPG 状态、长期记忆和新人物／物品的可操作性。代价是主回复更长、信息要求更高，需要同时保证叙事与结构化输出质量。
2. **把 daily 看作职责选择，而非一个可随手删除的名字。** 日常药物和限时状态属于基础游玩的可见结果；复杂周期／条件效果可单独讨论，但不能让已存在的状态无声停止工作。
3. **优先讨论调整多轮工具制作与战斗。** 它们需要“模型提出操作→本地结果→模型继续”的反馈，重建为一次请求比常规后处理合并更影响玩法。推迟或调整交互只是候选，尚未裁定。
4. **保留本地零调用能力通常不与预算冲突。** 随机事件、时间与地图派生结算、已有状态规则没有必要仅因取消独立 Agent 一并删除；是否减少它们仍应由玩法目标决定。
5. **剧情导演与普通任务分别决定。** 即使放弃独立剧情规划，接取、推进和完成普通委托仍有现成状态入口；反过来，保留任务表也不等于保留长期剧情导演。当前 Story 只接收大纲摘要与导演投影，剧情 Agent 能读完整幕后资料；合并后若保留完整规划，同一模型将同时知道谜底并写玩家正文，跨调用的信息隔离会变成提示词行为约束。见 `src/core/prompts/context-visibility.ts:52`、`:77`、`:117`，`src/core/prompts/agent-templates.ts:615`、`:644`。

制作还有介于完整保留和删除之间的候选：本楼 AI 写过程并声明制作意图，本地呈现真实检定结果卡，结果后的叙事留到下一楼。`buildCraftRequest` 与 `resolveCraft` 已提供本地请求构造和检定基础，见 `src/core/crafting/craft-request.ts:89`、`src/core/crafting/craft-resolver.ts:297`。代价是交互与叙事时序改变；把工具往返摊到多楼也不保证总调用次数减少。战斗没有同样现成的完整离线战斗引擎，不能据此类推。

上述优先关系来自现有调用与数据依赖的比较，是可行性推断，不是已验证的效果排序；昂贵或更强的模型也不能未经测试就视为能稳定完成全部合并职责。

## 5. 长聊和坏输出的真实代价

**一次摘要可以合进主回复，历史体量问题仍然存在。** 每楼新增摘要会持续累积；若始终全部发送，输入随回合数增长，最终受模型上下文容量限制。只保留近期窗口或使用本地检索会减少输入，但可能漏掉远期联系。前置回溯可以帮助挑选旧事，不能保证所有遗漏都被找回。

现有 v2 用额外调用做事件归档详情重写、缺摘要补建和归档重试。这些能力不能原样搬入硬预算；停止自动补建意味着某楼坏摘要可能长期缺失，而非下一楼自动付费修好。见 `src/ui/lib/game-pipeline.ts:2934`、`:3023`、`:3061`。

**坏输出不能靠额外请求自动补齐。** 正文成功但结构块错误时，已有解析器可以报告／跳过无效内容，本地可解析部分也可以继续处理；这不保证所有游戏变化都被保存。不能为了“自动修复”突破主请求与回溯上限。现有角色更新解析与逐项提交边界见 `src/core/character/character-updates.ts:93`，`src/core/state/state-manager.ts:659`。

回溯也只能占一次请求：现有 v2 的格式重试会再调用模型，当前路径并不满足这一约束。见 `src/core/agents/agent-orchestrator.ts:1407`。具体坏输出体验仍待选择，本轮没有确定自动删除、静默回退或重发策略。
