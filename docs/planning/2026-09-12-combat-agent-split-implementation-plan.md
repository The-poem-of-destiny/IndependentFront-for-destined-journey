# 战斗 V3：主持人与敌方决策 Agent 切割实施计划

> 状态：**公开仓实现完成（2026-09-14）；2026-09-15 完整 gates 已通过，真实 LLM / 真机战斗待验收。**
>
> 设计核对基线：`master@9763aa4`。公开仓现已落地双会话、动态权限、角色可见性、失败暂停、
> 端点继承、设置开关与 UI；私有内容仓在本机不可用，正式 pack 同步与真实战斗证据仍保留待办。
>
> 配套计划：[叙事导演子 Agent](2026-09-12-narrative-director-implementation-plan.md)。
> 推荐先完成本计划，验证双角色运行后再接叙事导演；战斗运行期间叙事导演不参与。

## 1. 目标、判断与范围

应该切割，但切的是**模型职责、上下文与工具权限**，不是把一场战斗切成两个控制引擎。
保留唯一 Combat Kernel 和 Code Coordinator：主持人理解玩家意图并演绎已结算事实，敌方 Agent
只决定当前敌方行动。双方不通过自然语言互相审批普通指令，由 Code 进行唯一验证与提交。

首版命名与兼容裁定：

| 逻辑角色             | 持久 Agent id            | 显示名     | 说明                                                               |
| -------------------- | ------------------------ | ---------- | ------------------------------------------------------------------ |
| `combat_host`        | **`combat_v3`，保留**    | 战斗主持人 | 逻辑角色名不再注册成第二个配置 id，避免旧绑定/用户 prompt 无谓迁移 |
| `combat_enemy`       | **`combat_enemy`，新增** | 敌方决策   | 一场战斗一个敌方阵营决策会话，不为每个敌人分别开 Agent             |
| Coordinator / Kernel | 无模型角色               | 引擎内部   | 时序、骰子、合法性、事实和最终落库的唯一权威                       |

完成标准：

1. 两个模型会话独立；玩家私有输入、查询结果、敌方战术解释不能相互串入历史。
2. 敌方只能提交当前获准敌方单位的行动，主持人不能代替敌方普通决策，也不能替玩家编行动。
3. 普通动作没有“敌方提出→主持人同意”的额外 LLM 环；Code 执行后由主持人叙述结果。
4. 结算、回放、幂等、同批多命令和已有 UI 交互不退化；不重写战斗数值公式。
5. 旧 Agent 配置、自定义 prompt、内容包、端点绑定和失败路径均有可验证兼容策略。

本次不做：重构 V3 规则/伤害/词条引擎、增加战利品生成、实现完整战场迷雾、敌人自主改规则、
多阵营人格群聊、队友自主决策新系统、持久化战斗断点续玩、自动平衡难度。
`EffectChoice` 当前在 Coordinator 存在 `UnsupportedInM2` 分支，**拆 Agent 不等于把它实现了**；
本计划只确保不误路由、不伪装成功，完整接入另立范围。

## 3. 路由与权限契约

### 3.1 Code 组织战斗，主持人组织表达

| 时点/请求                | 负责方                        | 输出与边界                                                  |
| ------------------------ | ----------------------------- | ----------------------------------------------------------- |
| 开场                     | 主持人                        | 描述参战局面；此阶段仅查询，不开打、不换玩家指令            |
| 玩家 `PlayerCommand`     | 玩家输入→主持人               | 只翻译已给定意图；不明确时继续等玩家澄清，不自行补动作/撤退 |
| 敌方 `PlayerCommand`     | 敌方决策 Agent                | 为当前敌方单位选择合法动作，不产叙述正文或世界补丁          |
| 动作提交                 | Coordinator→Kernel            | 校验角色、窗口、单位、目标、槽位与 revision，按序 dispatch  |
| `BeginOutput` / 需要骰子 | Code                          | 沿现行 drawDice/SupplyDice，无模型掷骰                      |
| `BoundedAdjudication`    | Code 既有有界裁决通路         | 普通敌方动作不经主持人审批；模型建议不能代替内核校验        |
| `CharGenRequest`         | Code→既有召唤池/char_gen 侧链 | 保持原供给/校验/持久化边界，两战斗 Agent 不能直接造单位落库 |
| `EffectChoice`           | 显式不支持分支                | 清晰报告、停止该不支持路径，不交给任一 Agent 猜测补齐       |
| 结算事实产生             | 主持人                        | 只演绎已经提交的 facts，失败可回退事实展示，不撤销结算      |
| 战斗结束                 | Code 提交域命令→主持人总结    | 角色资源/FP/EXP 等沿原唯一落库路径；总结不重复结算          |

保留生产中的玩家自然语言入口和现有结构化命令入口；不得借切割把“攻击某目标”改成无输入自动
决策。已有 `player-input.ts` 可用于明确、可验证的兜底，但不能宣称任意自然语言都可确定性解析。
玩家侧单位的控制权沿当前 `RequiredInput`/side 语义，不借本次新增自动队友代理。

### 3.2 工具与命令边界

静态 Agent 工具列表不是权限验证器。新增 Code 内部 `CombatDecisionContext`，包含角色、session
标识、决策窗口标识、获准 actor、源 revision 和允许的命令种类；这些字段均由 Code 创建。
每次工具调用和每次出队提交都验证，不能只在开场验证一次。

- 主持人开场/结算/结束使用查询或纯文本模式，不持有普通行动权限；玩家决策阶段才给玩家动作工具。
- 敌方仅获当前敌方行动的 `declare_attack`、`declare_action`、`pass_slot`、`flee`、`end_turn`
  与受限查询；没有 `write_summary` 或通用写工具。敌方声明行动不直接发到玩家可见正文。
- `submit_adjudication` 不作为敌方普通动作工具开放。既有需要有界裁决的请求保留 Code 路由；
  主持人也只能在明确授权的有界请求窗口提案，六步边界验证及内核不变量仍是最终裁判。
  若合法特殊能力必须扩充敌方提案接口，应在 B0 对现有夹具核对并通过专门窄接口处理，不能
  退回“为兼容所以给敌方全部工具”。
- actorName 缺席使用 Code 绑定 actor；提供时必须按现有名字解析入口精确匹配该 actor。
  不接受模型自填 id 或伪造 revision；目标必须在当前允许寻址集合，未知/歧义名字明确报错。
- 未知工具、无权工具、错误阶段、错误单位一律工具错误，不翻译为 pass。查询未找到与越权应
  区分内部诊断，但对敌方不能用详细错误泄露隐藏对象是否存在。
- 同批 attack+action 保持顺序；每条执行前重验窗口与可用槽。中途 actor 死亡、战斗结束或控制权
  改变，剩余命令作废。只允许已授权同批命令使用现行逐条 revision 机制，不能自动重基线一个
  来自旧窗口的敌方决策；陈旧外部结果丢弃并按最新视图重新请求。

敌方的战术说明如需要诊断，使用独立可选短字段，不保存或索取模型隐藏推理；不进入主持人历史。
多命令去重使用 Code 生成并在同一逻辑提交重试中复用的 commandId，不重新请求后复用旧决策 id。

## 4. 信息隔离与会话模型

### 4.1 首版可见性策略

首版采用“敌方阵营共享战场可观察信息”，不实现逐单位视野、声音传播或秘密联盟知识。
这是一项明确的游戏信息策略，不能把它宣传为完整迷雾系统。

| 数据                               | 主持人                         | 敌方决策                                        |
| ---------------------------------- | ------------------------------ | ----------------------------------------------- |
| 当前玩家输入、战前私人对话         | 可见，为忠实翻译所需           | 不可见，只有已执行的可观察行为                  |
| 当前回合/当前 actor/己方槽位       | 按所需可见                     | 可见当前获准决策所需数据                        |
| 敌方阵营单位的资源、技能、装备     | 为主持/规则表达所需可查        | 可见自身阵营战斗所需数据，不附带人物秘密档案    |
| 玩家侧 HP                          | 当前 Kernel 真值可用于演绎校验 | 只提供血量比例，不提供精确 HP/maxHP             |
| 玩家侧 MP/SP、未公开技能与背包     | 玩家指令需要时可查             | 不可见；已公开使用的名称/可观察效果可见         |
| 已执行行动、可见状态、可见战斗结果 | 可见                           | 过滤后的事实，不附带隐藏触发条件/未公开词条脚本 |
| 剧情秘密、隐藏身份、全局变量       | 不因切割扩大现有范围           | 不可见                                          |
| 敌方未执行计划/解释                | 不注入；只接收执行后的事实     | 留在自己的会话，不能把计划当战果                |

动态 HP/MP/SP/槽位/效果一律来自 Kernel 当前快照，静态技能/装备按参战时的合法定义及受控供给
更新来源组装。不能从未结算回数据库的角色记录取动态状态，造成“面板已受伤、查询仍满血”。

建议新增 `combat-v3/agent-visibility.ts`，纯函数负责字段白名单与可见事实累积规则：
首次只建立参战可观察信息；每次成功提交后从 facts 增量登记已展示的技能名/效果；未知不是没有。
没有可靠公开标记的字段默认不暴露，不从 narrative 文本反向猜出完整技能数据库记录。
需要从 UI 已公开字段构造白名单时逐项核对 `projection-ui.ts`，不能直接把 UI 对象整包发给敌方。

所有查询入口必须经过同一策略：`get_combat_state`、`get_character`、`get_inventory`、
`get_unit_detail` 都返回战斗限定投影，不能用换一个工具名绕过限制。敌方世界书也须限定为
规则/可见战斗背景，不整包复制主持人的筛选结果。缓存与调试导出同样不能绕过隔离。

### 4.2 两份会话、一个事实源

建议新增 `CombatAgentSessions`，分别保存 host/enemy 的 messages、client 与角色状态；
主持人 summary 单独属于 host，敌方无权填写战斗总总结。容器只持引用，不能深拷贝两套 Kernel。

- 主持人开场初始化；敌方在首次敌方决策时惰性初始化，避免没有敌方行动的战斗也多发一轮开场请求。
- 决策前投影当前快照；敌方后续收到自上次决策以来的可见事实与当前视图。
  主持人只收到已提交事实/玩家输入，不收到敌方未执行输出、查询回包或战术解释。
- host/enemy 的 system/template/history/query 结果、摘要及裁剪过程都独立；不能把同一 messages
  数组换一个 systemPrompt 就算隔离，也不能用包含两方秘密的统一摘要做上下文压缩。
- 一名敌人行动并结算后，再为下一名敌人投影最新状态；首版不并行预生成全队行动。
  敌方可在自己的会话内保持短期配合意图，但 Code 不保存另一份“队伍计划事实”。
- 两角色都沿战斗侧链会话运行，不直接塞入主 DAG Delta 会话；战斗总结仍按原接口交还主流程。
- 开战时固定模式、Agent 配置与端点；战斗途中改设置仅影响下一场。取消、换档或离开战斗时
  取消双方在途请求并销毁会话，旧运行结果不能进入新战斗。

## 5. 配置迁移、失败恢复与兼容

### 5.1 模式与默认配置

新增 `combatAgentSplitEnabled` 全局开关，首版缺省 false，作为试运行与回退入口；战斗开始时固定
该值。关闭走现行单会话路径，开启才执行本计划的隔离保证。旧模式不是“同样安全的双角色简版”，
只是兼容路线；后续默认开启或退役旧模式必须有真实验收证据及明确版本决策。

`combat_v3` 原 id/model 绑定保留，显示名明确为主持人；用户自定义 prompt/template 不覆写。
兼容期共享默认仍保留旧单 Agent 路径所需说明，拆分模式以独立、版本化的 host 角色契约收窄职责；
不能先删掉共享 prompt 的敌方决策教学，再宣称关闭开关时旧模式保持不变。两模式的实际组装分别测试。
拆分模式附加不可省略的角色契约与工具门禁，prompt 中旧的“控制所有人”文字不能扩大实际权限；
设置页提示自定义配置需要复核，可提供显式恢复默认，不自动清空用户内容。

`combat_enemy` 无独立配置时使用专用敌方默认 prompt/template，端点继承**当前已成功解析的主持人
端点**，不复制玩家历史、主持人自定义 prompt 或用户 API Key 到另一份持久设置。
用户给敌方显式选择端点后，使用自己的绑定；绑定失效 fail-closed，不能偷偷回退到主持人/别家。
内容包提供的本机 pool id 按现有来源判定规则处理并可见告警，不能冒充用户显式绑定。

`RunCombatV3Opts` 当前单 endpoint 接口需要向后兼容扩展，例如新增按角色解析后的端点配置；
旧调用者只传 endpoint 时两角色可使用同一已授权端点，但 client/messages 必须独立。
复用 `src/ui/lib/endpoint-resolver.ts` 与 `game-pipeline.ts` 的现行解析入口，不另造隐性路由器。
共享 URL+Key 的请求继续走同一 RPM 桶，不能因为 Agent id 不同各开一桶。

### 5.2 失败矩阵

| 失败                     | 规定行为                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------- |
| 主持人无法解析玩家意图   | 返回可解释错误并等待玩家补充；不自动防御、跳过或让敌方接管                          |
| 敌方网络失败/超时        | 沿既有有界客户端重试；耗尽后暂停于当前 RequiredInput，显示重试/退出入口，不默认弃槽 |
| 敌方输出未知或越权工具   | 工具错误回喂、保留当前状态；受工具轮数上限约束，耗尽后暂停，不无限循环              |
| 纯查询或空输出未形成命令 | 拆分路径视为未完成决策，不沿历史空命令 pass 兜底；触及上限后暂停                    |
| 陈旧结果/取消/换档       | 校验运行代次及决策窗口后丢弃，不能执行、叙述或写总结                                |
| 结算叙事失败             | 展示已提交 facts 的确定性简述，允许下一合法步骤；不重掷、不重放命令                 |
| 结束总结失败             | 使用事实摘要；已提交域结算不撤销、不再次发奖                                        |
| 不支持 EffectChoice      | 可见报告并保留原可恢复边界；不伪装选项成功，不擅自落库战果                          |

暂停是当前进程内保留 Kernel 和会话、允许重试的状态，不承诺刷新浏览器可恢复战斗。
“退出”沿既有退出/放弃语义，不偷偷转换成逃跑成功或胜利；UI 文案必须说明会发生的现有行为。
故障后不能静默切回单 Agent 接管本场敌人，那会破坏隔离与可复现性；关闭开关从下一场生效。

### 5.3 内容与可观测性

- 同步公开默认配置、Agent 设置目录/模板预览、历史默认指纹与正式内容仓战斗模板。
  新增敌方条目不得在旧 pack 缺字段时被清空；区分整包默认与用户覆写的现行三态语义。

## 7. 验收矩阵与回归门槛

| 场景                                 | 核心断言                                                           |
| ------------------------------------ | ------------------------------------------------------------------ |
| 玩家先手与敌方先手                   | 正确角色先被调用；没有敌方行动时不额外发敌方开场请求               |
| 多敌人连续行动                       | 后一个决策读到前一个结算后的状态；不批量并行猜测未来状态           |
| 玩家明确攻击/用道具/撤退/含糊输入    | 忠实解析或澄清，不生成玩家没选的动作，不改原规则成本               |
| 己方/对方详情和背包查询              | 所有查询工具遵同一策略；换名/换工具不能绕过白名单                  |
| 玩家私有计划诱导泄漏                 | 敌方实际 wire messages、工具回包与摘要均无该输入，不仅是 UI 没显示 |
| 精确资源与旧数据库态                 | 敌方看不到玩家私有资源；可见动态值与当前 Kernel 一致               |
| actor 伪造、未知名、非当前阵营       | 工具错误，revision/槽位/HP 不变，不能被 pass 兜底掩盖              |
| 同批攻击+动作                        | 两个合法命令按序执行；第一条导致终局/换 actor 时第二条作废         |
| 重复 commandId / 陈旧决策窗口        | 幂等仍成立；旧窗口不能靠重写 revision 获得执行权                   |
| 幽灵文本与敌方计划                   | 未 dispatch 的动作不进入玩家正文；主持人只叙述已提交 facts         |
| 网络失败、空输出、工具轮数耗尽       | 有界失败后暂停；玩家不被自动行动，敌方不被自动弃槽                 |
| 叙事/总结失败                        | 不二次执行、不二次扣资源/发 EXP/FP；事实简述可接续                 |
| 有界裁决、召唤                       | 仍走原 Code/Kernel 验证，不给敌方自由改规则工具                    |
| EffectChoice                         | 明确不支持，不因测试有内核能力就宣称协调器/UI 已接通               |
| 取消、换档、下一场重开               | 双会话清理，迟到结果丢弃，新 battle 无旧战斗历史                   |
| 开关、旧配置、旧 pack、自定义 prompt | 关闭保持兼容；开启门禁生效；内容缺新条目有专用默认                 |
| 用户端点失效与 pack 默认失效         | 按来源处理，用户显式选择不被无声换 provider，RPM 仍共桶            |

优先扩展既有测试：`coordinator.test.ts`、`projection-agent.test.ts`、`kernel.test.ts`、
`replay.test.ts`、`player-input.test.ts`，以及战斗 contract/复杂词条夹具。
新增权限和会话隔离测试，直接捕获 mock client 接收到的完整消息与工具定义；不能只测试投影函数
就声称实际发送链路不会泄露。UI 回归覆盖双角色标签、等待/重试、取消与战斗结束返回主流程。

代码提交前运行聚焦 Vitest 与 `npm run gates`。公式与内核回放在固定 Command/dice tape 下应保持
一致；双角色 LLM 选择可能不同，不把“战果和旧模型完全一样”当迁移成功标准。

真实验收至少包含普通单敌、多敌配合、玩家复杂意图、敌方受伤后的重决策、撤退/终局、
有界能力及失败恢复场景；使用当前正式内容包，并按
[调试循环手册](../reference/debug-loop-handbook.md)记录版本、配置及脱敏证据。
逐动作统计 host/enemy 的真实调用与 tokens、首动作/后续动作延迟、重试/排队次数。
结构性性能门槛：普通敌方行动没有主持人审批调用，没有敌方额外开场 LLM 调用；查询工具往返
单列，不假装一次决策只可能一次网络请求。质量门槛：无越权动作、私有输入泄漏与重复结算。
