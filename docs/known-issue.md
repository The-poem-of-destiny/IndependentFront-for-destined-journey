# Known issue: 地图 v1.2 结算的两条收益丢账（低危，只少给钱不多给钱）

状态：已定位根因、暂不修（2026-08-19 Fable 审查裁定记档；同轮的三条已修，见 `docs/CHANGELOG.md`
「地图 v1.2」条目）

两条都出在按期结算（`src/sillytavern/map-dynamics.ts` 的 `settleTileFacts` +
`src/sillytavern/state-manager.ts` 的 `syncMapFactsSettlement`），方向一致 —— **丢的一律是玩家该拿的钱，
不会凭空多给**，且都不产生数据损坏：

1. **周期性降档摧毁的玩家产业，摧毁前已到期的收益期数不入账**（`map-dynamics.ts:settleTileFacts`）——
   结算的三步是「周期效果 → 到期移除 → 收益收集」，而收益收集扫的是**活下来的**建筑：一次跨 90 天的
   前进里，若第 30 天那一拍的降档摧毁了最高号槽里的玩家酒馆，它在第 0–30 天本该入的那一期就随它一起
   消失了。**状态到期有中窗折算**（`windowEnd` 压到到期日，那条注释专门讲了这件事），收益没有对应的处理。
   修法要把收益收集与逐期结算**交织**（每跨一期先记这一期的账，再执行这一期的进度效果），
   那会把 `settleTileFacts` 现在这条平铺的三步流程改成逐期循环 —— 与本轮修的三条不同源，故暂记档。
2. **事实态先落库、收益 patch 由锁外自提交消费；自提交失败则该窗口的期数永久丢失**
   （`state-manager.ts:syncMapFactsSettlement` + `applyTimeAdvance` 末尾的自提交）——
   `gameTime` 与事实态在**锁内**已经落库，收益却只是往 `patches[]` 里塞了一条 delta，
   由锁外那次 `commitChatState` 统一提交（锁内嵌套提交 = 同 saveId 自等死锁，这条约束本身是对的）。
   而时间账本是**零簿记推导**的：入账点全靠 `anchorDay` 推，没有「上次结算到哪天」这个游标 ——
   一旦那次自提交失败（抛出，或补丁级失败落进被调用点丢弃的 `errors` 数组），下一次结算的窗口起点
   已经是新的一天，那笔钱再也推不回来，玩家侧只表现为「这个月的产业收益没到」。
   修法方向：给收益补丁一条独立的失败重试/补账通道，或把入账点从「纯推导」改成带一个最小已结算游标
   （后者与 ADR-33「零 lastSettled 簿记」的裁定冲突，需要重新裁定）。

# Known issue: 远程素材 v1 审查残留（三条低危，有界不腐蚀数据）

状态：已定位根因、暂不修（2026-08-18，PR #114 合并时 Fable 审查裁定 MERGE 后记档）

三条均出自审查复核，窄边界、计数守恒、不产生数据损坏，修复优先级低：

1. **孤儿队列 FIFO 还账错位**（`src/ui/lib/asset-url.ts:397`）——`evict(id)` 后，同 id **新 URL**
   持有者的 `release` 会先偿还**旧 URL** 的孤儿账。交错序列〔A 持旧 → evict → B 取新 → B 先于 A
   释放〕会提前吊销 A 正在显示的旧 URL（死图），且新 URL 的计数搁浅到 A 释放为止。计数守恒不泄漏；
   代码内注释已声明这是刻意的近似。
2. **evict 微任务窗口**（`asset-url.ts:257/419`）——若 evict 恰落在 `load()` 缓存+持账与发起方
   `liveOnly` 判定之间，发起方拿到 null（不欠账）但孤儿账上多一笔无人偿还的引用，一条 object URL
   滞留到该 id 下一次 release 或 `revokeAll`。有界、自限。
3. **墓碑在声明临时缺席时被误剪**（`src/ui/stores/asset-store.ts:2218`）——墓碑剪枝以**当次**声明集
   为准：世界书被临时停用（或工坊项目关闭）期间跑过一次同步，其槽位的墓碑即被剪掉；重新启用后，
   玩家刻意删除的远程素材会复活。与「作者真的撤回了声明」在当前设计下不可区分。
   后续方向：剪枝改「连续 N 次同步缺席才剪」，或以已安装书集（而非启用条目集）为剪枝键。

背景与修复记录见 `docs/CHANGELOG.md`「远程素材 v1」条目的审查轮小注。

# 已关闭记录：UI-01 捏人页禁用装备仍可被选中

状态：已关闭（2026-08-29 产品裁定接受现有行为，无需修复）

来源：`docs/reviews/2026-08-12-ui-review.md` §UI-01（P0，评审原文称「应阻断发布」）。

产品裁定：本项目是单人游戏，创角点数与资格不承担多人公平性、服务器权威或共享经济边界。玩家主动绕过限制只改变自己的开局难度，属于允许的玩家自主选择，不构成缺陷或发布阻断项。

## 技术现象（保留作历史证据）

点数不足 / 种族不符 / 身份不符的物品在装备选择步骤会渲染成灰色禁用卡片，但玩家点卡片**内部**
那颗「选择」按钮仍能把它加进选择集，最终提交出负点数或不满足资格约束的存档。

## 根因

三层校验全部缺席，禁用只是**外观**：

1. `CreateStepSelections.vue:129` 把 `!store.canSelect(item)` 传成卡片的 `disabled` **外观**；
2. `SelectableCard.vue:26` 的卡片级 click 守卫（`!disabled && !selected`）**只守卡片本体**——
   内层「选择」按钮在 `SelectableCard.vue:65` 无条件 `$emit('select', item)`，`@click.stop`
   还顺手挡掉了冒泡，那颗守卫根本轮不到；
3. store 侧不复核：`addEquipment`/`addItem`/`addSkill`（`create-store.ts:703/713/728`）只查
   `isSelected` 去重，**一次都没调 `canSelect`**（`create-store.ts:691`）；
   `CreateStepSelections.vue:43` 的 `handleSelect` 同样是直通。

## 处理结论

不实施代码修复，不再列入发布阻断或缺陷待办。除非未来产品边界发生变化并获得重新授权，不应重新引入强制校验。

# Known issue: EJS 世界书与持久角色状态冲突

状态：新存档生成链已修复；旧污染存档仍需重建（2026-08-03）

## 现象

创角时选中含 EJS 的内置命定核心后，Story Agent 可能仍生成与核心世界书不一致的设定。
已观察到的妲丽安案例中，模型把她描述为不知自身来历、近乎无机质的系统核心，而世界书定义的
妲丽安是掌管九十万六百六十六册幻书的「黑之读姬」。

## 当前处理链

世界书进入 Agent 提示词前依次经过：

1. 当前存档的 `metadata.enabledWorldBookEntries` 选择过滤；
2. `AgentConfig.worldBookIds` 的 Agent 可见性过滤；
3. 条目 `enabled` 激活过滤；
4. 静态条目与动态条目分区；
5. 含 `<%` 的动态条目由 QuickJS 预渲染；
6. 渲染结果通过 `{{LORE_BOOK_STATIC}}` / `{{LORE_BOOK_DYNAMIC}}` 注入提示词。

EJS 执行失败时，条目会按原文注入并记录到 Debug 导出的 `ejs.fallbacks`。EJS 世界书的渲染
结果本质上仍是 Agent 提示上下文；除获授权的 `vars` 差量外，它不会自动创建、覆盖或校正
`CharacterState`。

## 已修复部分

内置 `system_core` 和 `character` 条目出厂使用 `enabled: false`，表示默认不全局注入。此前即使
存档明确选择了 `system_core:413`，条目仍会在通用 `enabled` 过滤阶段被删除，根本到不了
QuickJS。

现在，存档明确选中的内置 `system_core` / `character` 条目会在存档过滤边界克隆为启用态。
该覆盖不作用于工坊或用户书；它们仍遵守条目自身的 `enabled` 设置。

后续调试又确认并修复了两处独立问题：

- 旧设置可能保存了一份与引擎内置 Story 默认模板相同的模板。规范预设已经自行注入世界书、历史和
  本轮输入时，这份默认模板会把三者再次追加，导致提示词成倍膨胀。现在保存值与内置默认模板等价
  时按默认模板处理，不再重复装配；真正不同的自定义模板仍保留原行为。
- 当存档明确选择 `system_core:<uid>` 且相应 Agent 的世界书开关启用时，运行时会把
  `system_core` 授予 Story 与 `char_gen`。新配置的 `char_gen` 出厂白名单也已包含
  `system_core`，避免角色生成链只能根据 Story 的二手描述猜测命定核心人格。
- 工坊项目可用保留标签 `system/core` 声明命定核心语义。该项目被当前存档启用的条目会把对应
  `workshop:<projectId>` 授予 Story 与 `char_gen`；未启用条目、普通工坊项目及其他 Agent
  不会因此扩大可见性。标签匹配忽略大小写及首尾空格。

另已修复开场请求重复生成：旧逻辑在整条长管线结束后才写入 `openingPromptConsumed`，页面在管线
期间重新挂载会再次提交同一开场。现在生成前先原子认领；第二个管线实例无法重复启动。

## 尚未解决部分

最新妲丽安调试记录已经满足以下条件：

- EJS 后端为 `quickjs(wasm)`；
- `ejs.fallbacks` 为空；
- Story 提示词包含妲丽安世界书的「九十万六百六十六册幻书」「全知的黑之读姬」等正文。

但该存档在修复前已经由 AI 生成并保存了一个冲突的「妲丽安核心」角色状态。这个状态把她定义为
不知道自身起源的无机质系统，并在 Story 提示词中作为当前角色状态再次注入。模型最终采用了这份
更靠近当前回合的持久状态，而不是世界书设定。

`request_dispatcher` 仍只负责从 Story 正文识别请求，不直接读取 `system_core`；命定核心的权威
原文由 Story 与实际创建角色档案的 `char_gen` 读取。

> 🔴 本节结论**自 2026-08-16「管线并行化」（写队列地基 + 4 层管线 + 侧链旁路化）落地后未重新复核**——
> 那轮改动动了状态落库的时序与顺序，本节的观察是在它之前取的。真机迭代时需要重跑一遍上面三条判据。

## 影响与临时处理

- 修复会让现有存档从下一次提示装配开始收到正确的 EJS 世界书正文，但不会自动修复已经落库的
  冲突角色、任务、记忆或剧情事实。
- 已污染存档需要重建相关命定核心状态，或新建存档后重新验证；仅刷新页面不能清除旧状态。修复
  不会静默覆盖已经发生的剧情和玩家数据。
- 不应通过把内置核心条目的全局 `enabled` 改成 `true` 来规避问题，否则多枚命定核心可能同时注入。

## 后续修复方向

1. 为已有冲突状态提供可控的重建或校正路径，不静默覆盖玩家产生的正常剧情状态；
2. 增加从存档选择、EJS 渲染、角色生成到 Story 回复的端到端真机回归测试；
3. 评估超大 Story 预设的上下文预算，避免非重复内容本身造成注意力稀释。
