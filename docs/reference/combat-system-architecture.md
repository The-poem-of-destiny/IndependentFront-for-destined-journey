## 一、设计目标

### 1.1 定位

战斗系统是一种**较为严谨的解决 AI roleplay 中战斗过程靠口胡的办法**，在保证严谨的情况下增加趣味性。

### 1.2 设计原则

| 原则 | 含义 |
|------|------|
| **趣味性 / 开放性优先** | 不限制大部分技能效果，AI 能发挥创造性 |
| **数值严谨兜底** | 关键数值（HP/生死/检定）由代码保证，防止口胡/作弊 |
| **文字语言 ↔ 程序语言对接** | AI 的自然语言效果描述，通过可计算的数值字段翻译成代码能处理的形式 |
| **对齐世界书效果规则** | 效果分类、登神强度、buff 结构等直接采用世界书定义，不另起炉灶 |
| **魔改不照抄** | 战斗协议骨架保留，执行机制（脚本/事件/管道）改造 |

### 1.3 核心设计哲学

世界书原版战斗**完全由 AI 演算**（鲁棒性强但数值飘、不可重现、易作弊）。本架构引入代码做**纯计算兜底**，AI 做**创造性决策**，两者通过 EventBus + modifier 对接：

```
AI（创造性、模糊）─── event / modifier ─── 代码（严谨、确定）
意图解析、叙事         ←→                  骰子、检定、伤害管线
战意行为选择                                HP 扣减、生死判定
```

## 二、核心架构：管道 + 中间件

### 2.1 数据流模型

战斗流程的每一步都是「**参数 → 主函数 → 参数**」的变换：

```
输入参数 ──→ 【主函数】──→ 输出参数
              │
              └─ 执行中通过 EventBus 触发事件
                 物品/buff 函数链式处理参数
```

- **主函数** = 代码（确定性纯计算，如攻击检定、伤害管线）
- **物品/buff 函数** = 脚本（可编程，能改参数）
- **主函数做仲裁**：脚本只改参数，不能直接出伤/扣血；最终结算权在主函数

### 2.2 单向链不回环（铁律）

同一事件的多个订阅者按**链式顺序**执行，前一个的输出是后一个的输入：

```
初始参数 → 戒指1 → 戒指2 → 戒指3 → ... → 最终参数
```

- ✅ 可预测（方向唯一）
- ✅ 无死锁（不回环）
- ✅ 可调试（链上每步可打 log）
- ✅ 执行有界（链长 = 订阅者数）

### 2.3 同构契约（统一来源）

以下四类"效果来源"使用**完全相同的契约结构**，EventBus 不区分：

| 来源 | 生命周期 | 例子 |
|------|---------|------|
| 物品 | 持久（装备/卸下） | 幽怨之剑 |
| 技能 | 持久（装备/遗忘） | 火球术 |
| Buff/Debuff | 临时（回合/驱散） | 流血、狂暴 |
| 套装/天赋 | 永久 | 二件套加成 |

## 三、脚本契约

### 3.1 契约结构

每个"效果来源"携带一组脚本条目，每条是一个完整的「订阅契约」：

```ts
{
  itemId: "幽怨之剑",
  scripts: [
    {
      event: "attack.before",           // ① 订阅哪个事件
      source: "幽怨之剑",                // ② 物品来源（静态身份）
      owner: null,                       // ③ 持有人（动态，装备时填）
      handler: (ctx, params) => {        // ④ 实际函数（读 params，返回 params）
        return { ...params, baseDamage: params.baseDamage + 200 }
      },
      condition: null,                   // ⑤ 触发条件（可选）
      priority: 0                        // ⑥ 链内执行顺序（可选）
    },
    // ...可订阅多个事件
  ]
}
```

### 3.2 source vs owner（必须区分）

| 字段 | 性质 | 用途 |
|------|------|------|
| `source` | **静态** | 物品/技能的"身份证"，永远不变。用于追溯、调试、buff id 前缀 |
| `owner` | **动态** | 当前持有人。装备转移/丢弃/掉落时变。用于反比例函数读持有者状态、**在场过滤** |

### 3.3 套娃机制

buff 的脚本和物品的脚本**完全同构**。物品能给角色上 buff，buff 内部也能挂脚本（再挂 buff、触发伤害、改属性…）：

```
物品"幽怨之剑"
  └─ handler 调 ctx.applyStatus(target, "流血")
        └─ "流血"buff 自己带脚本清单，注册到 EventBus
              └─ round.end 触发 → 扣血
              └─ 流血还能再触发别的 buff（递归）
```

**递归深度限制**：现有 `subscription-manager.ts` 有 ≤10，战斗场景建议收紧到 ≤5，防止递归爆炸。

### 3.4 在场过滤

事件触发时，EventBus 检查订阅者的 `owner` 是否在当前参战者列表：
- 在场 → 执行
- 不在场 → 跳过（"远在天边的剑不响应战斗事件"）

## 四、效果系统（对齐 #265160）

> 世界书 [品质效果限定]（#265160）定义了一套完整的效果体系。本节基于它**改造落地**，不照抄原文。

### 4.1 六大效果类别（modifier 类型系统）

所有效果的 modifier 必须归为以下 6 类之一。代码根据类型分发到管线对应步骤：

| 类别 | 说明 | 进管线的位置 | 例子 |
|------|------|-------------|------|
| **固伤** | 额外固定伤害 | Step 6a（+ 固伤） | "攻击时 +200 物理伤害" |
| **百分比** | 乘算修正（增伤/减伤/增效） | Step 6（× 系数） | "伤害 +20%" |
| **资源** | 固定 HP/MP/SP 变动、护盾 | 直接结算 | "恢复 500 HP" |
| **检定** | 命中/闪避/先攻/抵抗修正。**五维只能走这类** | 检定阶段 | "命中 +5"、"力量检定 +2" |
| **附加效果** | 增益/减益/控制/DoT/HoT | 通过 buff 系统（事件触发） | "流血：每回合扣 5% maxHp，持续 3 回合" |
| **特殊机制** | DR/穿透/暴击倍率/召唤/光环/规则改写 | 各自管线步骤 | "DR 10%"、"穿透 20%" |

**铁律**（来自 #265160）：
- 严禁直接增减五维（体/智/敏/力/精），五维相关效果只能写为"检定修正"
- 混合伤害须标明各类型占比
- 高品质可带低品质效果，但数值按对应品质执行

### 4.2 登神强度顺序（priority）

世界书给了明确的 9 级强度（可直接作为 priority 枚举）：

```
普通(0) < 微弱要素(1) < 完整要素(2) < 微弱权能(3) < 完整权能(4) 
       < 微弱法则(5) < 完整法则(6) < 神位(7) < 神国(8)
```

**冲突仲裁规则**（#265160 原文）：
> 若与登神长阶冲突，**以登神层级高者为准；低阶效果不得压过高阶登神能力**

**代码实现**：每个效果带 `divinity` 字段（9 级枚举），冲突场景比较等级，高的压低的。

**冲突场景**（需要比 divinity 的）：
- 攻 vs 守（神位伤 vs 常规盾）
- 施加 vs 抵抗（法则控制 vs 常规抗性）
- 互斥的同类效果（两个"无法行动"效果叠加时，取高阶）

**非冲突场景**（不比 divinity，正常走管线/叠加）：
- 两个独立伤害叠加
- 同源 buff 刷新

### 4.3 效果转化表（AI 创造性 → 代码可算）

AI 生成效果时，"不可直接计算"的概念必须按下表转化（来自 #265160，作为 item_gen 的生成约束）：

| 不可计算概念 | 转化为 |
|-------------|--------|
| CD / 冷却 | X 次/战斗 |
| 施法速度 / 吟唱时间 / 攻击速度 | 先攻检定修正(+N) |
| 距离 / 射程 / 位移 | 标签"范围:X"（目标数）或状态"无法行动 N 回合" |
| 移动速度 | 先攻/逃跑检定修正(+N) |
| 范围面积（半径 X 米） | 标签"范围:X"（目标数） |
| X% 概率触发 | d20 ≥ 阈值 |
| 暴击率 / 闪避率 / 命中率 | 对应检定修正(±N) |
| 元素抗性（火抗/冰抗） | 伤害类型减免% 或 DR% |
| 仇恨 / 嘲讽 | 控制状态"标记 N 回合" |
| 耐久 / 弹药 | "X 次/战斗"或消耗品 |

### 4.4 modifier 注入管线

collect_mods 事件触发时，物品/技能/buff 的 handler 返回 modifier，主函数根据类型分发：

```
collect_attacker_mods 事件
  ↓ 物品 handler 返回 modifiers
  ↓ 按类型分发:
    固伤   → 累加进 Step 6a 的 fixedDamageBonus
    百分比 → 累加进 Step 6 的乘算系数
    检定   → 累加进命中/闪避/先攻修正
    特殊   → DR/穿透/暴击各归其位
    附加效果 → 不进管线数值，转为 buff 施加
    资源   → 直接 HP/MP/SP 结算
```

## 五、Buff/状态系统（对齐 [状态规则]）

> 世界书 [状态规则] 定义了 buff 的完整契约。本节对齐它的字段与规则，结合本架构的 id 命名做落地。

### 5.1 Buff 6 字段定义

```
效果名称: 简练标识符（如中毒、灼烧、流血）
类型: 增益 | 减益 | 特殊
层数: 当前层数（默认 1）
剩余时间: 数值+单位
来源: 分类(物理/魔法/精神/环境) - 施加者/技能/物品 ; 解除/触发条件
效果: 数值化描述
```

### 5.2 去重规则（id + 同源/异源）

**buff id 构造**：
```
有上级: "上级.状态名"     例 "幽怨之剑.流血"
无上级: "状态名"           例 "暴雨"（系统/环境 buff）
```

**实例标识** = `(owner 角色, buff id)`
- A 身上的"幽怨之剑.流血" 和 B 身上的"幽怨之剑.流血" 是**两个独立实例**
- 同 owner + 同 id = 同实例

**去重规则**（对齐 [状态规则] "同源叠加刷新时间+增层，异源独立计时"）：
- **同源**（同 id，即同一来源再次施加）：刷新剩余时间 + 增加层数
- **异源**（不同 id，不同来源）：独立计时，共存
- 例：A 的剑挂"幽怨之剑.流血"，C 的毒挂"毒瓶.流血"，两者在 B 身上共存

**AI 生成 buff 的约束**：item_gen 生成 buff 时，id 必须带物品/技能前缀（上级），裸名只允许代码预置的环境效果使用。

### 5.3 生命周期（4 种，对齐 [状态规则]）

| 类型 | 剩余时间写法 | 对应主人之前定的分类 |
|------|-------------|---------------------|
| 战斗型 | X 回合 | 随回合数减少 |
| 持续型 | 永久 / 直至解除 | 不随回合数减少（不可堆叠） |
| 触发型 | 直至触发（触发后移除或转持续） | 特殊 |
| 条件型 | 直至条件消失（如离开毒雾） | 不随回合数减少 |

战斗↔非战斗自动转换：进战时"X 分钟"→"X 回合"，脱战时反向。

### 5.4 结算时机（对齐 [状态规则]）

```
回合开始前  → 结算【增益】（攻击+20%、先攻+5 这类）
     ↓
   行动阶段
     ↓
回合结束后  → 结算【减益】（流血、中毒、燃烧 DoT）
```

**铁律**：增益在 `combat.round.start` 结算，减益在 `combat.round.end` 结算。

### 5.5 layer 处理

`layers` 作为 handler 的**自由参数**，由脚本自己读写。架构不规定 layer 的语义，由 buff 类型决定：
- DoT 类：layer = 层数（每层 +X 伤害）
- 增益类：layer = 强度等级
- 时间型：layer 可复用为剩余回合

### 5.6 状态交互（对齐 [状态规则]）

- **覆盖**：同名同源取高效果或刷新时间
- **豁免**：目标的体质/精神或种族特性可豁免特定来源/类型
- **驱散**：需对应来源分类（物理/魔法/精神/环境）的净化手段

## 六、战斗流程与 Event 时间线

### 6.1 战斗生命周期

```
战斗发起
  Story 或 vars_update 输出 <combat_trigger>
  ↓ 等当前轮角色/记忆/物品生成都完成
  ↓ 唤起独立战斗面板（从上方或下方滑入），正文流暂停
  ↓
回合循环 ────────────────
  ↓ （见 6.2）
  ↓
战斗结算
  ↓ 摘要回注正文（≤500 字，当用户消息注入 Story）
  ↓ 正文流恢复
```

### 6.2 回合循环

```
回合开始
  ├─ combat.round.start    （结算增益、刷新总览面板）
  ├─ combat.turn.start      （轮到某单位）
  │
  逐单位行动（按行动轴）:
  │  每单位 1 攻击 + 1 动作（可交替）
  │  ├─ 攻击行动（见 6.3）
  │  ├─ 战术动作（AI 调函数）
  │  ├─ combat.morale.check → result（条件触发）
  │  └─ combat.turn.end
  │
  所有单位行动完 ↓
  └─ combat.round.end       （结算减益、DoT tick）
```

### 6.3 攻击行动子流程（管道视角）

```
combat.attack.request (AI→代码)
  payload: 攻方/守方/技能/意图层级(AI已判定)/消耗
     │
     │ 【意图对抗检定】（代码，纯数值）
     │
combat.dice.roll (代码→脚本)  ← 随机数事件，脚本可改骰值
     │
combat.attack.collect_attacker_mods (代码→脚本)
  攻方装备声明 modifier（5 戒指在这里）
     │
     │ 【攻击检定】d20+优劣势+闪避 → 评级（代码）
     │
combat.attack.hit / .miss (代码→脚本)
  命中分支：挂 buff 类脚本在 hit 触发
     │
combat.attack.collect_defender_mods (代码→脚本)
  守方装备声明 modifier（2 盾甲在这里）
     │
     │ 【8 步伤害管线】（代码，纯数值）
     │ 【生死判定 + HP 扣减】（代码，红线）
     │
combat.attack.damage (代码→AI)
  传最终伤害+HP 变更
  赫卡忒式"濒死保护"在这里救场
     │
combat.attack.result (代码→AI)
  完整面板数据，AI 生成叙事
```

| 19 | `combat.settle.complete` | 代码→AI | 结算完，AI 写摘要 |

## 七、计算分工：代码 vs AI

### 7.1 代码管（纯数值，确定性）

- 骰子生成（含事件链处理后的最终骰值）
- 先攻计算 + 行动轴排序
- 意图对抗检定（公式：`(攻方T×5+d20) vs (守方T×5+d20+难度)`）
- 攻击检定（优劣势 + 闪避 + 评级）
- 8 步伤害管线
- HP/MP/SP 扣减（**红线：AI 不能直接动 HP**）
- 生死判定（**红线：HP ≤ 0 = 死亡，不可协商**）
- 回合资源（1 攻击 + 1 动作的硬约束）
- EXP 计算（单体 = 目标 Lv × 目标层级战斗系数，集群衰减）
- buff id 去重 / 层数刷新

### 7.2 AI 管（创造性，模糊）

- **意图解析**（自然语言 → 意图层级，纯 AI，代码不插手）
- **战术动作决策**（格挡/移动/道具，AI 调 `$combat.*` 函数）
- **范围目标选取**（AI 圈定打哪几个）
- **集群判定**（"≥3 同类低级单位"——同类由 AI 判；判定为集群后只生成 1 个代表，其余乘法）
- **战意结果选择**（从结果池挑投降/溃逃/嘴炮…）
- **FP 奖励**（根据"表现"，AI 创造性评估）
- **战利品生成**（itemThink）
- **登神等级判定**（AI 生成效果时，按叙事判定 divinity 等级）
- **战斗叙事**（HP% 对应伤势描写等）
- **战斗摘要**（≤500 字）

### 7.3 对接点

| AI → 代码 | 代码 → AI |
|-----------|----------|
| `attack.request`（带意图层级） | `attack.damage` / `attack.result`（数值结果） |
| `morale.result`（行为选择） | `morale.check`（HP<阈值触发） |
| `settle.loot` 返回 | `settle.complete`（EXP/FP） |
| modifier（6 大类之一） | event 触发（含 params） |

## 八、8 步伤害管线（含 modifier 注入点）

```
Step 1  初始伤害 = 关联属性×10×层级系数 + 技能威力 + 武器攻击力
        (多段/连击: 总和 ÷ N)
        ── 📥 检定类 modifier 在此之前已计入命中/闪避
Step 2  多段分割
Step 3  穿透修正: 有效防御 = 守方防御 × (1 − 穿透%)        [特殊机制-穿透]
Step 4  装备减免: 伤害 × (有效防御 / (有效防御 + 2000))
Step 5  类型减免: × (1 − 属性减免%)
          物理: (体+力+敏)×0.25% | 能量: (精+智)×0.4% | 精神: 精×0.8% | 真实: 0
Step 6  × 评级系数 × 意图系数
        ── 📥 百分比类 modifier 累加进乘算系数
Step 6a + 额外固定伤害
        ── 📥 固伤类 modifier 累加进此项
Step 6b × 攻击次数
Step 7  DR 修正: × (1 − DR%)                              [特殊机制-DR]
Step 8  集群修正: × 1.5                                    [仅目标为集群]
        ── 📥 登神 priority 在冲突场景仲裁（高阶压低阶）
```

**登神 priority 作用机制**：在 Step 3（穿透）和 Step 7（DR）阶段，如果攻方 divinity 高于守方对应效果的 divinity，低阶效果被压制（等效穿透/无视 DR）。具体映射见 [§十三 待确认](#十三-待主人确认清单)。

## 十、战斗 UI

**独立战斗界面**（不照搬世界书 `<action_info>` XML 文本面板）。

### 10.1 布局

- **唤起方式**：从屏幕上方或下方滑入，正文流暂停
- **风格**：类似 Agent 对话流的独立战斗面板

### 10.2 暴露内容

| 区域 | 内容 |
|------|------|
| 敌方区 | 敌方角色 + 三属性 |
| 我方区 | 我方角色 + 三属性 |
| 输入区 | 对话框（用户/敌人行动都走这里） |
| 角色选择 | 输入框上方选我方角色 → 暴露该角色技能/装备 |
| 普通攻击 | 用身上装备直接攻击的快捷入口 |

### 10.3 交互模型

- 用户输入队友行动 → AI 主持人理解意图 → 调 `$combat.*` 函数
- 敌人由 AI（Combat Agent）控制
- 战斗面板数据从 `combat.attack.result` event 来，前端组件渲染（不再是 AI 生成的 XML）

## 十一、Combat Agent

**定位**：战斗主持人（Game Master），全部负责函数调用。

### 11.1 四步流程

1. **初始化**：根据正文上文 + request_dispatcher 指令，判定参战人数、敌我、骰先攻
2. **回合控制**：每个回合控制一个角色，思考技能/攻击（**仅敌人**；队友由用户输入）
3. **判输赢**：智能判断——死斗→一方死；切磋→认输/打晕/嘴炮…
4. **结算 + 摘要**：EXP 结算 → 总结战斗 → 结束 → 摘要发送给正文 Agent
